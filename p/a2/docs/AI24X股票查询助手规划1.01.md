# AI24X股票查询助手规划 1.01（最精简、最优化、最高效上线）

> 定位：内部小圈子“免费体验”小产品。  
> 原则：前端少暴露、少敏感话术；**计次/会员/邀请/数据代理后端化**；先上线验证，再分阶段迭代。

---

## 0. 合规/风控基线（必须写进产品与开发）

### 0.1 页面内容与话术（尽量低风险）
- **保留**：`仅供学习研究演示 / 非投资建议 / 自行决策` 类免责声明（必须常驻可见）。
- **避免**：
  - 收益承诺（如“稳赚”“翻倍”“躺赚”）
  - 明确指令式建议（如“立刻买/必须卖/目标价”）
  - 公域强营销裂变话术（如“二级返佣/团队收益/拉人头”）
- **信号文案建议（不强制，后续可 A/B）**：
  - `小底/底/买/卖/顶` 可保留，但避免在公开页面写“买入/卖出建议”；更多用“关注/转强/转弱/高位预警”等状态语。

### 0.2 运营模式（MVP阶段更稳）
- **MVP**：只做“赠送体验次数/赠送VIP天数/抵扣金（不能提现）”这类权益。
- **二级收益（现金/返佣）**：后期可私域小范围试点，但不建议在前端公开展示“层级/返佣/收益”字样；如必须做，至少：
  - 触发条件必须是“真实付费”
  - 严格封顶、风控、留痕对账

## 1. 产品定位与用户路径（MVP）

### 1.1 目标用户
- 内部圈子用户：需要快速查个股/指数、看均线与“信号提示”。

### 1.2 核心用户路径
1. 打开页面 → 登录（最少一步）
2. 搜索/选择标的 → 查看K线/均线/信号
3. 次数不足 → 看到“剩余次数/到期”与“邀请送次数/赞助开通”
4. 继续使用/转化

### 1.3 “一次查询”如何计次（推荐定义）
- **一次 = 一次成功加载某标的 + 某周期**（日/周/月分别计）
- **短时间重复不扣**：同标的同周期 30 秒内不重复扣
- **失败不扣**：无数据/接口失败不扣

---

## 2. 技术总架构（最小可上线）

### 2.1 必须后端化的东西（前端不可信）
- 次数/VIP/邀请关系/发奖：全部在后端
- 数据接口代理：前端不直连腾讯/新浪/东财

### 2.2 推荐形态
- **前端**：保留现有 `research/leishen/demo.html`（后续可改名为产品页）
- **后端**：一个轻量 API 服务（Node/Fastify 或 Python/FastAPI 二选一）
- **存储**：SQLite 起步（最快），后续换 Postgres
- **缓存**：内存缓存起步，后续 Redis

---

## 3. API 设计（MVP 必须）

> 所有 API 都需要：鉴权（token）+ 基础限流（账号/IP）+ 日志留痕。

### 3.1 鉴权/账号（与主站 `api` 统一真源）
- **身份**：注册/登录/验证码真源在 **`api.ai24x.com`**（`/v1/auth/*`）；本站 **代理** `POST /api/auth/request_code`（邮箱 OTP）、`POST /api/auth/sms/send`（短信）、`POST /api/auth/register`、`POST /api/auth/login`，浏览器只打 `a` 同域。
- **JWT**：`api` 的 `SECRET_KEY` 与行情官 `AI24X_JWT_SECRET` **必须一致**；`sub` = 平台用户 id；本站依赖解析后 **`ensure_platform_user`** 写入本地 `users`/`quota`。
- `GET /api/me` → 当前用户、会员状态、剩余次数（仍读本地表）

### 3.2 次数系统
- `POST /api/quota/consume`（扣次，参数：`secid, period`；服务端做“30秒内不重复扣”）
- `GET /api/quota/status`（剩余次数、到期时间、当日已用等）

**配额口径（已落地的更科学版本，便于中线产品运营）**

- 免费：**30 次/周 + 6 次/天**
- VIP：**500 次/周 + 150 次/天**（月卡 99 的核心权益口径建议）

### 3.3 邀请（一级裂变：MVP）
- `GET /api/invite/my_code`（我的邀请码）
- `POST /api/invite/bind`（新用户绑定邀请码：只允许一次）
- `POST /api/invite/reward`（服务端自动触发即可，前端不直接调用也可）

### 3.4 数据代理（最关键：抗跨域/抗波动）
- `GET /api/suggest?q=xxx`（后端多源：东财suggest优先）
- `GET /api/kline?secid=...&period=day|week|month&count=...`
- （可选）`GET /api/snapshot?secid=...`（实时快照；不可用则降级）

---

## 4. 数据代理策略（多源兜底 + 缓存）

### 4.1 多源优先级（建议）
- K线：腾讯 →（备用）东财 →（备用）新浪
- suggest：东财 →（备用）本地缓存（最近查询）→（备用）简化搜索

### 4.2 缓存策略（MVP）
- suggest：缓存 10–30 分钟
- kline：缓存 30–120 秒（同标的同周期）
- 失败熔断：某源连续失败 N 次，短期降权/跳过

### 4.3 离线兜底（第二阶段可上）
- 缓存“最近一次成功 K线包”到数据库/对象存储 → 接口全挂时仍可展示“上次数据截至…”

---

## 5. 风控与反刷（MVP 够用版）

- 速率限制：按 `userId + IP`（例如每分钟 kline <= 30 次）
- 邀请防刷：
  - 绑定邀请码必须在注册后 X 小时内完成（可选）
  - 发奖需完成“首次有效查询/绑定手机号”等条件
  - 每日/每月奖励封顶
- 关键操作幂等：发奖/扣次必须有唯一键，避免重复发放

## 6. 分阶段路线图（一步步做）

### 阶段 1（MVP，上线验证）
目标：能登录、能查询、能计次、能邀请送次数、能稳定拿到数据。

**交付清单**
- 后端：鉴权、次数系统、邀请系统、数据代理（kline+sug）、基础限流与日志
- 前端：把 `demo.html` 的数据请求改为请求 `/api/*`；增加“剩余次数/登录态”
- 部署：HTTPS + 环境变量配置 + 基础监控（日志即可）

**验收标准**
- 未登录：只能看默认页/引导登录（或允许少量匿名次数，二选一）
- 登录后：可正常查 10+ 个标的，计次正确，失败不扣
- 邀请：被邀请人完成首次有效查询后，邀请人次数增加
- 数据源故障：主源挂了自动切到备用（至少不白屏）

### 阶段 2（转化增强）
目标：让“赞助开发（赠送VIP权益）”有明显价值，邀请更有吸引力且更抗刷。

- 赞助开发 → 赠送 VIP 权益（更低风控口径）：
  - **对外口径**：不写“收费/付费”，统一写“赞助开发”或“支持开发”
  - **用户获得**：赠送 VIP 权益（例如不限次/大额度、更多历史数据、自选列表等）
  - **页面展示**：仅展示“权益内容 + 到期时间 + 赞助入口”，避免“收益/返佣/层级”类措辞
- VIP 权益建议（可分档）：
  - 不限次/大额度
  - 更多历史数据（例如 500 → 2000/5000）
  - 自选列表/收藏（提升留存）
- 奖励升级：赠送 VIP 天数 / 抵扣金（不能提现）
- 缓存增强：Redis、失败熔断、离线兜底

### 阶段 3（工具化）
目标：形成稳定工具体验。

- 提醒订阅（站内/企业微信）
- 参数档位（保守/标准/激进）
- 导出图片/导出信号
- 回放与统计（VIP）

## 7. 第一阶段开发清单（按顺序执行）

> 你后续只要按这个顺序做，就能最小成本上线。

### A. 后端（优先做，打通后前端改动最小）
- [ ] 初始化后端项目（Node/Fastify 或 FastAPI）
- [ ] 基础配置：`PORT`、`JWT_SECRET`、`DB_PATH`、`RATE_LIMIT`
- [ ] 数据库表（SQLite）
  - [ ] `users`（id、手机号/unionid、创建时间）
  - [ ] `sessions`/`tokens`（可选）
  - [ ] `quota`（userId、plan、expiresAt、remaining、dailyUsed、dailyResetAt）
  - [ ] `invite_codes`（userId、code）
  - [ ] `invite_relations`（inviteeId、inviterId、createdAt）
  - [ ] `quota_ledger`（userId、secid、period、consumedAt、idempotencyKey、result）
  - [ ] `reward_ledger`（inviterId、inviteeId、rewardType、amount、createdAt）
- [ ] 鉴权接口：验证码登录（先假验证码也行，后续接短信）
- [ ] 次数接口：`/api/quota/status`、`/api/quota/consume`（含 30 秒去重）
- [ ] 邀请接口：生成邀请码、绑定关系、触发奖励（幂等）
- [ ] 数据代理：`/api/suggest`、`/api/kline`（腾讯优先 + 备用源 + 缓存）
- [ ] 基础限流与日志

### B. 前端（只做“改请求 + 显示额度”）
- [ ] 把 `EM_SUGGEST/TX_FQ/SINA` 的请求替换成 `/api/*`
- [ ] 每次成功查询前：先调用 `/api/quota/consume`
- [ ] 顶部/角落显示：剩余次数 + 登录入口（极简）
- [ ] 邀请入口：复制邀请码（不写复杂裂变文案）

### C. 部署（最简）
- [ ] 选一个服务器或容器（单机即可）
- [ ] 反向代理（Nginx/Caddy）
- [ ] HTTPS（证书）
- [ ] 日志：按天滚动
