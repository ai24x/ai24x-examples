# 《山海渔》开发推进流程（推荐顺序）

> 目标：最快验证 **「垂钓 → 卖鱼 → 升级」闭环**，且与已定口径一致：**`fisher-api` 真源 + 原生小程序**（见 `架构与落地汇总.md`、DEC-0009）。

---

## 结论：先做什么？

| 顺序 | 做什么 | 是否必须 |
|------|--------|----------|
| **1** | **`fisher-api` 最小后端**（健康检查、登录占位、抛竿/结算、读资产） | **必须** |
| **2** | **原生「小程序 Demo」**（只接你的 API，不做假经济） | **必须**（首期交付形态） |
| **3** | **网页版 Demo**（同一 API 的极简 H5 或静态页 + `fetch`） | **可选**（加速联调与给非微信环境演示） |

**不推荐**：先做「纯网页完整游戏 Demo」再迁小程序 —— 交互与运行环境差异大，容易做两遍；更推荐网页只做 **API 调试壳**（甚至用 Swagger / curl 即可）。

---

## 阶段 0：仓库与工程占位（0.5～1 天）

- 在 `p/game/fisher/` 下已具备 `api/server/`（FastAPI）、`miniprogram/`（微信开发者工具导入 `miniprogram/` 目录）。  
- 本地默认 **`http://127.0.0.1:18041`**（`scripts/start_api.cmd` 或 PM2 `fisher-api-18041`）；数据库 **仅 PostgreSQL**（`FISHER_DATABASE_URL`，见 `api/server/.env.example`）。  
- 约定：环境变量前缀 `FISHER_*`、`/v1` 前缀。

---

## 阶段 1：`fisher-api` 最小真源（2～5 天）

**目标**：没有小程序也能用 HTTP 证明「钱和鱼变对了」。

建议最小接口（名称可调整，语义建议保留）：

- `GET /health`  
- `POST /v1/auth/wechat`（或分步：`code` → session / token；首版可 mock 联调）  
- `POST /v1/game/cast` 或合并为 `POST /v1/game/fish`（含冷却校验 → 返回渔获）  
- `POST /v1/game/sell`  
- `GET /v1/me`（金币、积分、竿等级、仓库摘要）

**数据**：用户一行 + 库存/流水表能记下变化即可。

---

## 阶段 2：小程序 Demo（与阶段 1 重叠后半段，3～7 天）

**目标**：真机手感 + 微信合法域名流程跑通。

- 单页或双页：`index`（水面 + 抛竿/拉杆）+ 可选 `inventory`。  
- 所有改金币行为 **只走 `wx.request`**。  
- 动效：浮漂、咬钩、波纹（`transform` 写法见 `产品规划-山海渔-完整版-v1.0.md`）。  
- 微信开发者工具：配置 **合法域名** 指向 `https://fisher-api.ai24x.com`（或本地内网穿透域名）。

---

## 阶段 3（可选）：网页 Demo = API 联调壳（0.5～2 天）

**用途**：不用微信工具也能点按钮打 API；方便给合伙人看数据流。

- 一页静态 HTML + 内联 JS，或极简 Vite 页面，部署在 `fisher.ai24x.com` 子路径。  
- **不做**与小程序 1:1 的动效与布局复刻；只验证 **同一套 API**。

本仓库已提供本地 H5：`p/game/fisher/web/index.html`（主站）、`p/game/fisher/web/archive/history-legacy.html`（历史封存旧联调页）；端口见 `docs/PORTS.md`，默认 `18002`。

---

## 阶段 4：迭代产品阶段二、三

按 `产品规划-山海渔-完整版-v1.0.md` 的阶段表，在 API 层依次加：市价快照、离线收益、排行、UGC 与审核队列等；小程序逐页接新接口。

---

## 验收标准（Demo 算「完成」）

- [ ] 连续 20 次抛竿冷却在 **断网重连 / 杀进程** 后仍正确（服务端为准）。  
- [ ] 金币、库存与后端数据库一致，浏览器改包改不了真数据。  
- [ ] 小程序体验路径：**抛竿 → 咬钩 → 拉杆 → 卖鱼 → 数字变** 在一分钟内可走通。
