## 1. 角色拓扑：主脑、AI 助手、四台副脑

### 1.1 主脑（你）· 总指挥官与学习主体

**身份**：负责人、产品决策者、**唯一集成与发版拍板者**、AI 编程学习者、智能体任务指挥官。  
**主工作区**：本地高性能机 + Cursor（或同类 IDE）。  
**核心职责**：

- 维护 **单一 Git 仓库** 为唯一真相；所有副脑产出以 **可审查的提交（PR/合并）** 回流，避免「某台云机上的才是最新版」。
- **本地全栈联调**：API + 静态站 + 数据库契约一致后再标记可上预发布。
- 下达清晰任务、验收结果、查看日志与监控、组织修复优先级。
- **边学边做**：从「能跑」→「能改」→「能设计模块边界」→「能指挥多智能体分工」递进（见 §11）。

### 1.2 AI 助手（如 Cursor 内对话）· 参谋与副驾

**定位**：不写独断生产配置；**协助**你完成设计、拆任务、审代码、补测试思路、起草文档与检查清单。  
**协作原则**：你保留 **业务与合规最终决定权**；助手输出需经你 **本地运行与 Git 合并** 后生效。

### 1.3 副脑 01（dev-01）· 国际链路预发布 + 后端主力环境

**硬件参考**：上海 4C8G（公网可达）。  
**职责**：

- **核心后端**（FastAPI、业务逻辑、与 `db/` 契约一致）。
- **国际向预发布环境**：与新加坡 **同构部署**（独立配置、**非生产库或脱敏库**），用于公网 HTTPS、真实延迟、发版前最后一道 gate。
- **不做**：把预发布当「随意试验库」；不做与生产混用的密钥。

**不做**：长期替代本地集成；不单独成为「第二套真相仓库」。

### 1.4 副脑 02（frontend-01）· 首席体验与增长官

**硬件参考**：上海 2C8G（内网/公网按你实际为准）。  
**职责**：

- **官网、控制台、文档站**（与仓库 `web/` 一致）：纯 HTML/CSS/JS 路线可延续，重 **可访问性、加载与转化**。
- **内容与增长资产**：SEO 基础（标题、描述、结构化数据、sitemap）、多语言落地、活动页；后期承接 **自媒体文案草稿、GEO 本地化页面模板、发布队列**（人审后发）。
- **7×24 潜力**：定时任务、内容队列、监控「索引/可用性」类脚本可放独立轻量进程，**与生产 API 解耦**，避免抢新加坡资源。

**不做**：未经合并直接改生产机上的文件（一切回 Git）。

### 1.5 副脑 03（ops-cn-01）· 国内线与合规预留

**状态**：可长期低占用，**不等于闲置**：用于 **国内合规预研、备案路径、国内解析/CDN 演练**。  
**职责**：

- 未来国内业务：**预发布 / 灰度**，与国内支付与内容策略对齐。
- **可协助测试**，但 **不可替代** 新加坡面向的国际支付、国际 SEO、海外延迟体验；国际上架前仍以 **副脑 01 预发布 + 本地** 为主验证链。

**不做**：在未完成合规与产品决策前，对公提供与新加坡同级的用户服务（避免双轨数据混乱）。

### 1.6 副脑 04（ops-sg-01）· 新加坡 · 国际生产官

**定位**：**唯一对外生产环境**（按当前总纲）。  
**运行**：API、PostgreSQL（或主从）、Nginx、TLS、备份、监控、限流与风控策略落地。  
**职责**：

- 部署已 **通过预发布验证** 的版本；变更可回滚。
- **用户数据、业务日志、计费相关数据** 的存储与备份策略以本环境为准（具体架构随规模升级，原则不变）。

## 4. 核心必做功能（MVP 六项 · 避免无限返工）

1. 用户注册 / 登录 / 控制台（与后端契约一致）  
2. API Key 创建 / 管理 / 权限  
3. 唯一接口 + 免费 / VIP 自动分流（同一 URL）  
4. 按 Token 计费 + 余额不足拦截  
5. 微信/支付宝/PayPal 充值 + 订单 / 分成 / 提现（按监管与平台规则实现）  
6. 二级推荐返利（比例与规则以控制台与协议为准）

未列功能 **默认不做**；若做，须过「是否影响六项闭环」评审。

---

## 5. 免费 / VIP 自动区分（接口层原则）

- 无 Key / 免费 Key → 免费通道（日额度 + IP / 用户维度限流）。  
- 付费 Key → VIP 通道（计费、调度优先级）。  
- **客户端始终同一地址**：`POST /v1/chat/run`，不在客户端切换域名。

## 6. C2C 个人 Key 与分成（原则固化 · 参数可配置）

### 6.1 免费 Key

仅用于体验引流：**不参与分成、不参与结算**（与运营策略一致时可调，但须在文档公示）。

### 6.2 付费 Key（按实际消耗结算）

- **分成与平台抽成不锁死固定比例**：默认可参考 Key 持有者 **70%** / 平台 **30%**，实际以 **类目、供货商等级、促销与实验** 动态配置；随真实流水与风控数据 **收敛 take rate**（见 **§17**）。  
- 结算节奏：**日结或 T+1 可用**（以实际实现与风控为准）；**最小提现额、冻结期、拒付处理** 写入协议与控制台。  
- 用户可设 **单日最大消耗** 等风控上限。

### 6.3 定价策略

- 各模型 **明码标价**；平台售价相对上游官方价保持 **可解释区间**（示例：**0.75～0.85** 折或 **1.2～3.0** 倍加价系数的不同组合），**按区域、类目、是否独家供给** 分表维护，避免隐性加价。  
- **综合成本**须按真实 **输入/输出 Token 比例** 核算（见 **§17** 公式），禁止用「输入价 + 输出价」简单代替百万 Token 综合成本误导决策。

---

## 7. 返利与提现（原则固化）

- 二级推荐：**10% + 2%**（以协议为准）。  
- 资金用途：**抵扣 API 费用** 或 **提现至 微信/支付宝/PayPal**。  
- 最低提现（示例）：**$10**；手续费按通道实际收取。  
- 审核：**1～24 小时** 量级（可随风控调整）。

## 8. 顶层共创（对外专业 · 对内一人可控）

### 8.1 AI 合伙人

贡献资源（如 Key、拉新、生态协作）→ **贡献值与分红权**（**非股权**，以平台规则与协议为准）。

### 8.2 指挥官联盟与生态对接

开放 **可管控的联盟/合作接口与规则**；拉新归属与返利 **以系统记录与协议为准**；主脑保留 **规则制定与异常处置权**。

### 8.3 增长与品牌

- 接口与文档中统一品牌露出（如 **Powered by AI24X** 等，具体文案与频率需平衡体验与合规）。  
- **每一次合理曝光** 以不损害开发者体验为前提。

## 9. 安全风控（自动运行 · 可降级不可「炸」）

1. 新用户低免费额度 + 行为检测，防刷。  
2. C2C Key **用户自控消耗上限**。  
3. 异常 IP / 频率 / 异常消耗 → **熔断、验证码、人工复核**（分级）。  
4. 生产 **最小权限密钥**；**预发布不得使用生产密钥**。  
5. 对外错误信息 **不泄露内部栈**；详细错误仅日志。

## 10. 分阶段路线图（建议 · 可按周调整）

**原则**：先 **闭环与观测**，再 **规模与营销自动化**。

| 阶段 | 目标 | 产出物 |
|------|------|--------|
| **P0 · 骨架** | DB 契约、健康检查、认证链路、`/v1/chat/run` 通一条真实/模拟链路 | 可演示的端到端调用 |
| **P1 · MVP** | 六项核心中 **用户+Key+计费+单模型稳定路由** | 预发布可压测 |
| **P2 · 商业化** | 微信/支付宝/PayPal、订单、返利与控制台闭环 | 新加坡生产候选版本 |
| **P3 · 国际化与增长** | 英文默认文档与信任资产、SEO/落地页、支付拒付与客服话术、状态页、内容队列与监控 | 可持续运营漏斗 |
| **P4 · 国内线（可选）** | 副脑 03 合规与独立产品路径 | 与国内策略同步，**数据与国际隔离** |

**供货商扩展（与 §17～§19 对齐）**

- **一期（优先）**：以 **国内相对合规、文档清晰、可对接海外买家场景** 的 API 为主（见 **§18**），在新加坡生产侧完成 **观测、计费、熔断与对账** 闭环。  
- **二期**：在 **条款与商业路径清晰** 的前提下，接入 **国际直签或正规聚合渠道**（见 **§19**），补齐海外低延迟与多模态旗舰需求。

**30 天窗口**：可对应「4 周冲刺 + 缓冲周」；若课程与体力有限，**允许延长**，以 **里程碑** 而非日历绑架质量。

## 11. 你的成长路径：从开发者到「AI 编程师 + 智能体指挥官」

|------|----------------|------------------|

**周末**：以复习、轻量验收、文档整理为主；**避免堆新需求**，保护节奏。

## 14. 铁律汇总（OpenClaw / 副脑 / 本地共同遵守）

1. **唯一业务入口**：`POST /v1/chat/run`；免费 / VIP 自动区分，用户无感。  
2. **单一真相**：Git 仓库；集成在本地；副脑不各自为政。  
3. **生产数据与对外服务**：以 **新加坡** 为当前总纲下的生产承载；国内线 **独立演进**。  
4. **先闭环再扩张**：六项 MVP 未完成前，谨慎堆营销自动化与复杂分润。  
5. **风控与密钥**：预发布与生产隔离；对外错误不泄密。  
6. **愿景**：让开发者与合作伙伴在规则透明、技术可靠的前提下，追求 **Token 使用自由与可持续收益**——**具体收益以实际运营与协议为准**，规划文档不构成承诺。  
7. **扩展议题**：生态裂变见 **§15**；是否引入区块链见 **§16**，默认 **不实装**。  
8. **商业与供给**：主战场、供给分层、动态 take rate、一期/二期供货商与接入方案见 **§17～§19**；**禁止**在未完成上游条款矩阵评审前，将多源「免费额度」打包为稳定商业 SLA。

## 15. 生态共建与自主裂变（提前规划）

**目标**：上线后吸引更多人 **自愿** 参与——贡献优质 Key、文档与建议、分享拉新获利，并形成 **可复制的正向循环**（非传销、以产品与规则透明为前提）。

### 15.1 参与角色（上线前可在文档与控制台「占位说明」）

| 角色 | 贡献什么 | 得到什么（原则） |
|------|----------|------------------|
| **终端开发者** | 调用量、反馈、案例 | 稳定 API、透明计费、文档 |
| **Key / 容量提供方（C2C）** | 合规可用的上游 Key 或资源 | **分成**（已有规则）+ 控制台数据 |
| **推广者** | 邀请注册与消费 | **二级返利**（已有规则）+ 可追溯邀请关系 |
| **共建者（非代码）** | 优质文档、翻译、教程、FAQ | **声誉标识 / 小额激励 / 周边**（可选，需预算与防刷） |
| **建议者** | 功能建议、Bug、路线图讨论 | **公开致谢、优先级投票权（轻量）** |

### 15.2 产品侧可提前埋点（MVP 后可迭代）

1. **邀请链路闭环**：专属链接 / 邀请码、**归因清晰**（点击→注册→首消）、控制台展示「邀请人数、有效消费、预估返利」，降低扯皮。  
2. **C2C Key 上架体验**：上传指引、**可用性检测**、失败原因可读、**质量分 / 延迟展示**（脱敏），让「优质 Key」可被看见。  
3. **反馈与建议入口**：统一入口（控制台工单或 GitHub Discussions / 表单），状态机：**已收到 → 评估中 → 已采纳 / 暂不采纳（附简短理由）**，让贡献者感到被尊重。  
4. **公开路线图 + 更新日志**：哪怕极简，也能减少重复提问、吸引愿意跟版本走的共建者。  
5. **状态页（Status）**：可用性、事故公告，增强 **B 端信任**；信任是裂变的前提。  
6. **开发者物料**：一键复制的 **cURL / 各语言最小示例**、错误码表；降低传播摩擦。

### 15.3 激励与裂变设计（与合规）

- **钱**：返利与分成规则 **写死进协议与控制台**，变更提前公示；避免「口头承诺」。  
- **名**：贡献者榜单 / 徽章 / 「文档贡献者」**量力而行**（防刷：绑定账号、人工抽检）。  
- **权**：轻量 **路线图投票**（仅活跃用户或贡献者），增强参与感但不承诺治理权。  
- **合规**：邀请奖励须符合 **当地反传销与广告法规**；Key 上传须 **用户协议 + 责任边界**（滥用、上游封号等）。

### 15.4 运营与节奏（不必等「全做完」）

- **上线前**：准备《合作伙伴与推广者说明》一页、邀请海报文案、**3 个种子用户故事**（匿名可）。  
- **上线后 0～30 天**：收集 **10 条高质量反馈**、修 **Top 3 体验问题**，比盲目加功能更重要。  
- **持续**：每月一次 **公开小结**（改进了什么、下一步），利于自发传播。

### 15.5 技术侧预留（低成本）

- **Webhook / 事件**（后期）：订单、返利结算通知，方便推广者自建看板。  
- **联盟参数**：`utm_source`、邀请码在注册 API 中 **持久绑定**。  
- **审计日志**：关键操作可追溯，纠纷时可举证。

### 15.6 与「六项 MVP」的关系

生态与裂变 **依赖** 六项闭环（能注册、能付费、能返利、Key 能管）。因此：**先 MVP 稳定，再加重运营工具与声誉体系**，避免空转。

## 16. 区块链与链上模式（可选 · 原则）

**结论（一人维护 + 学习期）**：**默认不必要** 为 MVP 引入区块链。核心价值（聚合调用、计费、返利、风控）用 **PostgreSQL + 应用层 + 审计日志** 即可闭环；链上能力会显著增加 **运维、安全、合规与客服** 负担。

### 16.1 何时「仍不必」上链

- 结算与分润已在平台内可审计、可对账。  
- 用户要的是 **稳定 API 与清晰账单**，不是钱包与 Gas。  
- 无专职安全与合约审计资源时，**智能合约风险 > 收益**。

### 16.2 可替代「链」诉求的精简做法（建议作为「预留」而非链）

| 诉求 | 精简做法 |
|------|----------|
| 可追溯、防抵赖 | **追加型审计日志**（谁、何时、改了什么）、订单与结算 **幂等 ID**、定期备份与只读副本 |
| 对外「可验证」 | 定期发布 **透明度报告**（脱敏统计）；必要时对报告全文做 **文件级哈希** 公开（仍不必上链） |
| 贡献 / 积分 | 平台内 **积分与等级**（§15）；若未来要「可转让」再单独评估法律与产品 |
| 跨境结算 | 现有 **微信/支付宝/PayPal 等法币通道** 优先；链上稳定币涉及 **牌照与 AML**，一人公司慎入 |

### 16.3 若未来认真考虑链上，再评估的场景（非承诺）

- **链仅作可选增值**：例如「成就徽章 / 合作方凭证」类 **强合规** 场景，且与 **核心计费库表解耦**。  
- **绝不做**：把每日 Token 计费、余额、返利 **唯一真相** 绑在公链合约上（升级与纠纷成本极高）。

### 16.4 架构上「零区块链」也能做的预留

- 表设计：**结算单号、分账单号全局唯一**；账务 **只追加、冲正用反向单**（便于审计）。  
- 事件：**关键业务事件可记录为结构化日志**（供以后接 Webhook、BI，不必是链）。  
- 命名：产品中的 **Token** 指 **模型计费单位**，与 **加密货币 Token** 在对外文案中 **避免混用**，减少用户与监管误解。

## 17. 商业战略与供给分层（海外主战场 · 动态 take rate · 风险边界）

### 17.1 主战场：海外买家

- **信任资产**：英文控制台与 API 文档、错误码表、隐私与数据处理说明、**状态页（Status）**、退款与争议规则摘要。  
- **支付**：微信/支付宝/PayPal（及后续扩展）需预留 **拒付、冻结、手续费** 对 take rate 的侵蚀；企业客户路径可单独评审发票与对公。
- **体验诚实表述**：中国侧上游经新加坡出口时，对欧美用户标注 **延迟与可用性预期**（区域路由、降级链），避免「与本地同延迟」的过度承诺。  
- **合规表述**：对外不宣称「零合规成本」；日志留存、跨境传输、生成内容责任以 **用户协议 + 辖区律师意见** 为准持续迭代。

### 17.2 主模式：轻平台、重治理

- **平台核心能力**：统一 `POST /v1/chat/run`、路由、计费、限流、风控、分账、观测与对账。  
- **自营 / 集采定位**：**少量兜底**（保证默认有可用的付费 SKU），避免平台成为 **唯一主供货商** 导致垫资与价格战被动。  
- **扩张主力**：**认证合作伙伴（持授权或经销商协议）** + **BYOK（用户自有 Key 服务自有或约定范围）**。  
- **C2C 共享**：仅在上游 **用户协议明确允许** 或 **书面授权** 的场景下分级开放；**禁止**将「风险全转给供货商」写为对外法律依据——平台仍承担支付、治理与品牌责任。

### 17.3 供给分层（L0～L3 · 执行闸门）

| 层级 | 含义 | 典型用途 |
|------|------|----------|
| **L0** | 试用 / 引流额度（各上游官方免费层或活动） | 限配额、**不承诺生产 SLA**；条款公示 |
| **L1** | 平台集采 / 官方集成（平台作为客户） | 付费默认路径之一；可对账、可开发票（视上游） |
| **L2** | 认证供货方（企业 / 经销商） | 扩 SKU、区域价；合同 + 抽检 + 可选保证金 |
| **L3** | BYOK | 用户自有 Key；平台收订阅 / 流量费或低 take rate；责任边界写进协议 |

**闸门**：未完成《上游条款矩阵》（是否允许代理、转售、境外终端、日志要求）评审的供给，**不得**进入 L1 对外计费承诺。

### 17.4 定价、加价与动态 take rate

- **不锁死 30%**：平台留存率 **\(f_m\)** 按 **模型 m、类目（对话/代码/Agent）、渠道（官网/OpenClaw 插件等）、供货商等级** 配置，用 **A/B 与账务报表** 收敛。  
- **单位经济（内部必算）**：每百万 Token 上游边际成本  
  \[
  c_m = p^{in}_m \cdot r^{in} + p^{out}_m \cdot r^{out}
  \]  
  其中 **\(r^{in}:r^{out}\)** 取自平台真实调用日志统计（随产品变化），**禁止**用臆造「综合价」替代。  
- **终端价**：\(P_m = c_m \cdot (1 + \alpha_m)\)，**加价系数 \(\alpha_m\)** 分海内/海外、是否独家、是否企业 SLA 分表维护。  
- **平台毛利（近似）**：take rate × GMV − 支付损耗 − 退款与欺诈 − 基础设施与支持人力摊销 —— 对外路演须与内部表一致，避免混用「毛利率」口径。

### 17.5 增长：OpenClaw / Agent Skill / 插件分发

- **结论**：**可行且推荐**作为开发者分销渠道；官方提供 **1 个英文模板**（配置项、错误处理、隐私说明、版本化 API）。  
- **免费层**：仅作 **试用钩子**，须 **强限流 + 反滥用**；生产环境引导至 **付费 / BYOK**。  
- **维护**：对外 **模型别名稳定**（如 `deepseek/deepseek-chat`），上游 ID 变更在网关内映射，避免碎片 skill 集体失效。

### 17.6 明确禁止与高风险表述

- **禁止**：未做条款分拣时，将 **多家免费接口** 打包为「稳定商业套餐」并承诺高 SLA。  
- **对外话术**：优先使用「在授权与合规路径下整合中国侧高性价比与中文能力」，避免「全球最便宜」「90% 来自中国」等 **无法取证** 的绝对化用语。  
- **数据与报告**：市场体量、倍数、利润率等 **须标注来源与口径**；第三方生成的价目表 **须经各厂商官网复核** 后方可写入对外材料。

### 17.7 双轨战略：底层严把质量与交付 × 前端高效获取优质需求

**原则**：**有真实用户、有可持续流量，平台价值才成立**；但流量若建立在 **不可靠的调用与糊涂账** 上，会反向摧毁信任。因此采用 **双轨并行、职责分离**——**底层不妥协，增长不躺平**。

| 轨道 | 定位 | 必须做到的「硬标准」 |
|------|------|----------------------|
| **底层（后端 / 网关 / 数据 / 计费）** | **严把质量关、做好交付** | 统一入口行为可预测；**计费与对账可追溯**；关键路径 **可观测**（日志、指标、状态页）；上游 **熔断与降级** 不「静默失败」；生产变更 **可回滚**（见 §2、§9、§18.2） |
| **前端与增长（官网 / 控制台体验 / SEO / 社区与 Agent 分发）** | **尽可能高效触达「有需求、愿集成」的用户** | 英文文档与示例 **降低接入摩擦**；**渠道分层**（官网、插件、教程、合作方）便于收敛 take rate；增长活动与 **L0 试用** 挂钩，但 **不把无 SLA 供给包装成生产承诺**（与 §17.3、§17.6 一致） |

**「优质用户」操作化（避免唯注册数）**

- 优先看：**首次成功调用**、**7 日内重复调用**、**绑定支付或 BYOK**、**控制台内完成 Key 与模型选择**，而非单纯 PV/注册。  
- 内容与投放：**开发者向、可集成场景**（脚本、小产品、Agent）优先于泛流量；与 **§17.5** OpenClaw / Skill 分发协同。

**与「极端冲量」话术的关系**

- **不采用**「风险完全不顾、事后拆解」作为总策略；**采用**「**供给与账务底层守底线**，增长层 **积极试错**」：试错集中在 **文案、渠道、套餐组合、 onboarding**，而非 **计费错误、密钥泄露、支付争议失控**。

## 18. 一期：国内相对合规、可服务海外买家的供货商与 API 接入方案

**声明**：下表为 **候选清单**，落地前须 **逐家查阅最新用户协议、经销商政策、出口与跨境说明**，并完成法务与商务评审；**不构成对外承诺**。

### 18.1 候选供货商（优先对接顺序可按商务结果调整）

| 供货商 / 平台 | 代表能力 / 模型方向 | 面向海外买家的价值 | 接入前须核实（示例） |
|-----------------|---------------------|--------------------|------------------------|
| **智谱 AI（BigModel / GLM）** | GLM 系列，中文与通用任务 | 中文场景、企业向能力；可对外强调「中文刚需」组合包 | 是否允许向境外终端客户转售/代理；日志与数据出境 |
| **阿里云百炼（DashScope）** | Qwen 全系、部分第三方模型托管 | 文档较全；**新加坡等国际区域**节点利于海外延迟叙事 | 国际站与区域 endpoint；账单与发票主体 |
| **DeepSeek 官方 API** | 高性价比对话与推理 | 海外开发者关注度高；适合作为 **性价比引流 SKU** | 官方价目与 OpenAI 兼容接口版本；使用区域条款 |
| **硅基流动（SiliconFlow）** | 多模型云 API、开发者向 | 快速扩列模型清单；适合 **MVP 丰富度** | 转售与再分发条款；速率与公平使用政策 |
| **火山引擎（豆包大模型等）** | 字节系模型与平台能力 | 多模态与产品化能力 | 境外调用、合同主体、合规要求 |
| **百度千帆** | 文心等 | 国内生态与客户 | 境外 IP、代理政策 |
| **腾讯云（混元等）** | 通用与行业方案 | 大客户与合规组合 | 跨境与终端用户定义 |

**原则**：一期以 **1～2 家** 深度跑通 **计费 + 对账 + 熔断** 为主，再横向扩面；避免同时浅接十家导致密钥与账单失控。

### 18.2 统一 API 接入技术方案（工程规范）

1. **协议适配**  
   - **优先**：若上游提供 **OpenAI Chat Completions 兼容**（`base_url` + `Authorization: Bearer`），在网关内做 **请求/响应字段映射** 与 **流式 SSE** 统一。  
   - **否则**：官方 SDK 或 **HTTPS JSON** 独立适配器，统一出口为平台内部 `ChatRequest` / `ChatResponse` 模型。  

2. **密钥与配置**  
   - 生产环境仅存 **加密后的 Key** 或 **KMS 引用**；配置通过环境变量或密钥管理服务注入，**不入库明文、不进 Git**（见 `副脑统一操作手册`）。  
   - **一上游一凭据池**：便于轮换与按供货商熔断。  

3. **模型路由与别名**  
   - 对外稳定名：`类目/模型`（如 `deepseek/deepseek-chat`）；对内映射上游 `model` 字符串与 **版本钉扎**（避免上游静默升级导致质量漂移）。  

4. **可观测与计费**  
   - 全链路 **request_id**；记录上游 **HTTP 状态、latency、429/5xx 率**。  
   - Token 用量：**优先采用上游响应中的 usage 字段**；若无则按约定规则 **tokenizer 估算** 并文档说明误差范围。  
   - 落库字段与 `db/schema` 对齐，便于 **按供货商 / 模型 / 用户** 对账。  

5. **韧性**  
   - **熔断**：错误率或连续失败超阈时切换 **次要路由** 或返回 **可解释错误**（不泄露上游密钥）。  
   - **超时与重试**：幂等请求策略写清；对非幂等操作慎用重试。  

6. **国际生产部署**  
   - **新加坡（副脑 04）** 出网调用上游：优先选择 **上游文档明示可国际访问的 endpoint**；若必须经国内链路，须在架构图中标注 **延迟与单点风险**。  

### 18.3 一期验收（建议）

- 至少 **一条** L1 路径：**真实扣费 + 真实上游响应 + 账单字段闭合**。  
- 控制台可查询 **按模型消耗**；管理端可拉取 **与上游账单可对齐的汇总**（允许 T+1 延迟）。

## 19. 二期：国际相对合规、可交易供货商与 API 接入方案

**声明**：国际供货商涉及 **发票、税务、数据驻留、企业协议**；下表为 **候选清单**，须 **逐家签约或使用条款允许的集成方式**。

### 19.1 候选供货商（直签或正规渠道）

| 供货商 / 平台 | 典型价值 | 接入形态建议 |
|----------------|----------|----------------|
| **OpenAI** | 旗舰通用与生态兼容 | 直签 API；企业可走 Azure OpenAI |
| **Anthropic** | 长上下文与推理 | 直签 Claude API |
| **Google AI（Gemini API）** | 多模态与搜索结合类场景 | Google AI Studio / Vertex（企业）路径分别评审 |
| **Groq** | 低延迟推理 | LPU 推理 API；注意速率层级 |
| **OpenRouter** | 单端点多模型 | **平台作为客户**接入；注意「再聚合」条款与账单结构；模型 ID 与平台别名映射 |
| **Together AI** | 开源与定制推理 | API 与计价按官网 |
| **Mistral AI** | 欧洲向与多语言 | 直签 |
| **Cohere** | 嵌入与 Rerank 等 | 按产品需要启用 |
| **Azure OpenAI** | 企业采购与合规 | B2B 合同；与新加坡主体及客户属地匹配 |

**原则**：二期解决 **海外低延迟、旗舰多模态、指定合规路径**；与一期国内性价比供给 **组合成「统一账单」叙事**，而非重复堆同构廉价模型。

### 19.2 接入技术方案（在一期规范上的增量）

1. **区域路由**：按用户区域或自选 **优先走延迟最低且条款允许的 endpoint**；默认策略写入路由表并可观测 A/B。  
2. **再聚合商（如 OpenRouter）**：单独 **成本科目** 与 **故障域**；禁止与直签上游混用同一熔断统计，避免误判。  
3. **企业功能预留**：SSO、审计日志导出、VPC/专线类需求 **单独里程碑**，不与 MVP 六项混谈。  
4. **合规与数据**：各上游 **数据是否用于训练、日志保留期** 在控制台 **分模型披露**，便于海外买家选型。  

### 19.3 二期验收（建议）

- 海外用户 **P95 延迟** 与 **错误率** 在状态页分级公示；**旗舰 SKU** 与 **经济型 SKU** 分档 SLA。  
- **动态 take rate** 在「国内经济型 / 国际旗舰 / BYOK」等类目上 **至少各有一套可回滚的实验配置**。
