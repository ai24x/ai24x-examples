# AI24X—AI 无限 · 接口自由｜站点与子项目规划（国内优先验证版）

本文件定义 **主站** 与 **子项目池** 的统一规则，方便你按阶段逐步开发并持续追加新项目。

## 1. 目标形态（域名分层）

- **主站**：`www.ai24x.com`
  - 对外品牌、产品介绍、控制台入口、文档入口
  - 可先承载国内业务验证（小圈子 / 内测 / 灰度）
- **AI24X 统一 API**（旧称 Token Freedom API）：`api.ai24x.com`
  - 分阶段推进：先跑国内业务验证 → 成熟后再推国际版
  - 核心能力：7×24 小应用可用的统一 AI 接口（逐步补齐鉴权、计费、限流、观测）
- **AI 行情官｜灯塔版（1.01）（第一个子项目）**：`a.ai24x.com`
- 目标：中线波段辅助神器（股票查询 + K 线 + 信号参考）
  - 先用 MVP：后端代理数据 + 计次/会员/邀请后端化 → 再逐步增强

> 关键原则：**不同子域名 = 不同服务边界**。这样能把稳定性/风控/发布节奏隔离开，避免一个项目拖垮全站。

## 2. 仓库映射（单仓多项目）

### 2.1 主站（www）

- 代码：`web/`（纯 HTML/CSS/JS）
- 本地静态预览：`cd web && python -m http.server 8080`
- 生产建议：由反向代理直接托管静态文件（或由 `api/` 挂载也可以，但会把“主站可用性”绑到 DB/后端上）

### 2.2 AI24X 统一 API（api）

- 代码：`api/`（FastAPI + PostgreSQL 为主线）
- 说明：目前 `api/main.py` 会挂载 `web/` 作为同端口站点；开发时若只想预览页面，可使用 `SKIP_DB_INIT=true` 让服务不因 DB 不可用而退出。

### 2.3 AI 行情官｜灯塔版（1.01）（a）

- 代码：`p/a/`
  - 后端：`p/a/api/server/`（FastAPI + SQLite 起步）
  - 前端：`p/a/web/index.html`（正式入口）+ `p/a/web/demo.html`（基线备份）
  - 规划：`p/a/docs/AI24X股票查询助手规划1.01.md`（MVP 与分期路线图）
  - 权益口径：`p/a/docs/定价与权益口径（MVP）.md`

AI 行情官｜灯塔版（1.01）当前约定（国内优先验证版）：

- **身份真源（已定稿，见 `memory/decisions/DEC-0007-身份真源-api与行情官认票.md`）**：终端用户账号（手机/邮箱 + 验证 + 密码 + JWT）落在 **`api/`（`api.ai24x.com`）** 的 `auth_users` 表；**`a` 子域 `p/a`** 通过 **同密钥 JWT**「认票」，并在本地 SQLite/PG 同步 **影子用户**（`users.id` = 平台 `auth_users.id`）以承载配额/邀请/支付等业务表。
- **登录 / 注册（产品）**：**手机号 | 邮箱** 二选一；**注册**两条路均需 **验证码 + 密码**；**登录**为 **密码**（与 DEC-0006、主站首期一致）。本站 `p/a` 提供 **同域代理**（`/api/auth/*` → `api` `/v1/auth/*`），避免浏览器持有短信 internal key。
- **与全站账号口径（DEC-0006）——「统一又分离」**  
  - **统一**：对外同一套账号原则（手机+邮箱为主、微信后期）。  
  - **分离**：子域服务边界不变（行情业务仍在 `p/a`）；仅 **身份数据** 与 **JWT 签发** 收敛到 `api/`，后期 **Token 自由 / Key 计费** 直接挂在同一 `auth_users` 上扩展。
- **配额**：周额度 + 日上限（符合中线节奏，易运营与抗刷）
- **导出**：不提供导出到文件（优先站内粘性与会员功能空间）
- **行情上游与风控原则（上线必须遵守）**：
  - **统一走后端**：避免浏览器直连上游（跨域/拦截/口径不一致），把出口 IP 收敛到可控的服务器侧
  - **按需 + 缓存 + 并发合并**：把“用户侧风暴”变成“少量稳定上游请求”；失败要可观测、可降级、避免重试风暴
  - **付费备源预留位**：公共源抖动/封禁风险客观存在；必要时启用合规付费源做日K兜底（周/月由日K聚合）

## 7. 可借鉴的“社区捐助/积分门槛”商业模式（记录）

> 观察：TuShare Pro 采用“社区捐助/积分门槛 + 频次权限分层 + 推荐裂变增长”的组合拳，既覆盖基础用户，又能靠高阶需求自然付费，并把资源成本（带宽/算力/存储）用频控体系收敛到可持续。

对 AI24X 的可迁移点（尤其 AI24X 统一 API 与 7×24 AI 小应用）：
- **分层门槛而非按次扣费**：用“积分/等级”做权限门槛（不一定按次扣），降低心理负担；高等级换来更高 QPS、更大日配额、更稳定 SLA。
- **能力分区**：把“常规能力”（低成本/可缓存）与“高成本能力”（实时/长上下文/外部工具/高频）拆成独立权限包，便于定价与控成本。
- **频控即产品**：把限流/配额从“被动风控”升级为“产品化权益口径”，让用户理解并接受规则，同时保证平台稳定。
- **裂变增长**：把“邀请/贡献”与“权限提升”绑定（送额度/送等级），用可控的增长换取获客。

## 6. 端口分段规范（杜绝冲突，长期追加）

### 6.1 服务器（部署端口池：8000+）

约定：**服务器部署端口从 8000 起递增**，一项目一端口，新增项目依次追加。

| 项目 | 子域名 | 端口 |
|------|--------|------|
| 主站 | `www.ai24x.com` | `8000`（若纯静态也可不占端口） |
| AI 行情官｜灯塔版（1.01） | `a.ai24x.com` | `8001` |
| AI24X 统一 API | `api.ai24x.com` | `8002` |
| 未来项目 | `*.ai24x.com` | `8003+` |

### 6.2 本地（开发端口池：18000+）

约定：**本地开发端口从 18000 起递增**，与服务器端口池隔离，避免你本机同时跑多个服务时“线上表”和“本地表”互相打架。

| 项目 | 本地端口 |
|------|----------|
| 主站静态预览（可选） | `18000` |
| AI 行情官｜灯塔版（1.01）（p/a） | `18001` |
| AI24X 统一 API（api/） | `18002` |
| 未来项目 | `18003+` |

> 说明：端口只是“进程入口”，对外永远建议通过反向代理绑定到子域名（HTTPS），不要直接对公网暴露端口。

## 7. 国际站（出海复制）规划（同代码 · 分环境 · 强隔离）

目标：在**不复制仓库/不分叉代码**的前提下，把“国内已跑通的业务”复制到海外生产环境，形成**国际可用**的主站与统一 API 网关。

### 7.1 推荐域名与区域分层（最小复杂度）

结论（推荐）：**主站不新增 intl 域名**，统一使用 `www.ai24x.com`，用**多语言/地区切换**承接国内与国际访问；国际化的主要隔离点放在 **API 网关与数据层**。

建议保持“站点壳”与“API 网关”分层，并用**区域子域名**区分环境：

- 主站（同一域名，多语言承接）：
  - `www.ai24x.com`：语言/地区切换（可面向国际用户）
- API 网关（建议按区域拆）：
  - **对外统一入口**：`api.ai24x.com`（文档/SDK/示例/控制台统一只写这一条）
  - **预留（不对外公布，仅运维/灰度/应急）**：
    - `api-cn.ai24x.com`：cn 入口（可选）
    - `api-intl.ai24x.com`：intl 入口（可选）
- 子项目（按需复制到 intl，但仍保持独立边界）：
  - `a.ai24x.com`：AI 行情官｜灯塔版（1.01）（可先 cn 跑通，再评估 intl 是否需要）
  - `a-intl.ai24x.com`（可选）：AI 行情官｜灯塔版 intl 壳（同代码分环境）

> 原则：**API 按区域拆**是国际化的第一优先级；这样能把**数据、支付、上游供给**按区域隔离，而主站用多语言最低成本承接。

### 7.2 代码与目录策略（不复制 `api/`，用配置区分）

- **不新增 `intl/` 目录，不复制 `api/`**。同一套代码，通过环境变量切换：
  - **数据库**：cn 与 intl **必须分库**
  - **支付通道**：cn（微信/支付宝） vs intl（PayPal/Stripe 等）
  - **回调域名 / CORS 白名单**：按区域配置
  - **上游模型供给**：不同区域可用性与条款差异，路由表按区域维护

### 7.3 数据与账号策略（出海成败关键）

- **强制要求：分库分环境**  
  国内与国际生产的用户、订单、账单、日志、密钥策略**不混库**（避免合规与运营口径相互污染）。
- **账号是否互通（建议先简单）**：
  - **第一阶段（推荐）**：账号不互通——cn 与 intl 各自注册、各自计费、各自账单
  - **第二阶段**：再做统一身份（SSO）与区域映射（复杂度高，等 intl 跑通再上）

### 7.4 运行与发布（保持现有流水线）

发布仍遵循“本地 → 预发布 → 生产”的铁律；intl 与 cn 的差异主要在：

- 环境变量与密钥（支付/上游/回调）不同
- 数据库不同
- 反向代理与证书不同

端口与进程命名建议见 `docs/PORTS.md` 的 “intl 端口池与命名”。
