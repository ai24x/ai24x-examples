### 上游风控/出口 IP 风险（结论与观测）

- **线上“服务器统一出口 IP”确实更容易被上游按 IP 聚合风控**（行业常态），因此必须靠工程手段把“用户侧请求风暴”变成“少量稳定的上游请求”。
- **本地开发机出现 `ERR_EMPTY_RESPONSE` / `RemoteProtocolError` 不等同于“你点太多次”**：更像是 **本机网络路径/安全代理/DPI** 对 `push2his.eastmoney.com` 等域名不稳定或拦截；换机器/换热点可快速验证。
- **我们不是“爬虫抓全市场”**：当前实现是 **按需查询**（用户触发才请求），但一次查询可能包含 **并行/重试**（例如东财日/周/月并行、失败重试），因此要避免：
  - 无缓存的重复查询风暴
  - 失败后的高频重试风暴
- **已落地的降风险手段（力所能及）**：
  - **缓存**：内存 + SQLite（减少重复命中上游）
  - **singleflight**：同一 `(secid, period, count)` 并发合并（削 burst）
  - **熔断/退避**：腾讯侧已有雏形；东财侧以“失败返回 + 缓存”为主
  - **多源降级**：腾讯/东财/新浪（覆盖范围不同，口径需接受差异）
- **近期行为变化提醒**：板块 K 线从“浏览器直连东财”改为“走后端 `/api/kline`”后，**开发机上会更多表现为服务器出口访问东财**；这有利于解决浏览器跨域，但也意味着开发机网络若拦截东财，会集中体现在后端日志里。

### 可借鉴的“社区捐助/积分门槛”模式（记录）

- 观察：TuShare Pro 的“社区捐助/积分门槛 + 频次权限分层 + 推荐裂变”组合，对“Token+7×24 AI 小应用平台”很有参考价值：既能自助开通、又能用频控体系把成本与稳定性做成产品的一部分。
- 可迁移到 AI24X 的做法：
  - 用“等级/积分”做权限门槛（非强制按次扣费），让用户更愿意长期留存
  - 把高成本能力（外部工具、长上下文、更高 QPS、更高并发）拆成独立包，便于定价与控成本
  - 把配额/限流“产品化”（权益口径透明、可预期），减少对抗与误解
  - 邀请/贡献换权益，促进低成本裂变增长（注意幂等与风控）
