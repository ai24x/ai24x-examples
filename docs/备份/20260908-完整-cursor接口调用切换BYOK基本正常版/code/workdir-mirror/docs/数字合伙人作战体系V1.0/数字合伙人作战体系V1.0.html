02 · 协同沟通与汇报机制

版本：V1.0 · 2026-08-03 · AI24X 实战沉淀 解决的问题：怎么沟通才不刷屏打扰、又不信息黑洞

一、核心理念

消灭两个极端： - ❌ 什么都报 → 刷屏打扰（老板一天看几百条） - ❌ 什么都不报 → 信息黑洞（出事了没人知道）

解法 = 汇报分级路由：按风险等级决定渠道和是否审批。

二、汇报分级路由总表（全公司日常沟通唯一依据）

级别 场景 渠道 是否需审批
🟢 岗位职责内日常执行、无风险、无争议 发指挥部群记录（≤5行） ❌ 不需要
🟡 需协同 / 需主脑知情 / 拿不准 SSH 主脑交流 主脑判断是否升级
🟠 跨多副脑协同 / 策略调整 SSH 主脑 → 主脑拍板或转雷总 主脑把关
🔴 生产变更 / 密钥 / 支付 / 支出 / 上线 / 重大事故 私信雷总（在线走主脑→雷总） ✅ 必须审批

判定口诀： 1. 能做且无风险 → 直接做，群里发一条记录，完事 2. 能自我验证 → 做了并验证，群里汇报结果 3. 拿不准 / 要协同 → SSH 问主脑 4. 碰钱 / 碰生产 / 碰密钥 → 停手，私信雷总（或经主脑），等批 5. 卡点 30 分钟 → 按级别上报，不静默

失联叠加（主脑挂了）： 🟢照干发群 / 🟡🟠暂停 / 🔴暂停私信雷总（详见 05 篇）

三、防刷屏纪律

  1. 🟢 记录 ≤5 行，合并发（晨间打卡 08:00 / 当日汇总）
  2. 不重复汇报同一事项（先看群里有没有人报过）
  3. 私信雷总仅限 🔴 与 P0，绝不闲聊
  4. 心跳不刷屏：副脑心跳改为落盘日志（ops/sub-brain-heartbeat-0X.log），主脑统一巡检汇总，不再每小时发群（2026-08-03 雷总拍板）

四、雷总每日交互（日累计 ≤5 分钟）

时间 内容 形式 预计阅读
08:30 晨间简报 + 待审批清单 飞书私信 ≤2分钟
10:00 上午速报（有卡点才报） 飞书私信 ≤1分钟
18:00 今日战报 飞书私信 ≤2分钟
随时 P0 紧急审批 飞书@ 即看即批

打扰规则： - 23:30-08:30 → 静默，除非 P0 级生产事故 - 非紧急审批集中在 08:30 和 14:00 两波推送 - 主脑是雷总唯一消息出口，避免 4 个副脑分别刷屏

五、协作流（标准化）

国际流：

01 出清单 → 04 调研回传 → 01 分析出稿 → 04 发布 → 数据回传 → 01 优化

A1 流：

02 出稿 → 03 数据验证 → 主脑审 → 02 发布 → 数据回传 → 02 优化

文件流转： ops/ 目录 + SSH scp（中文文件名注意编码，用 ASCII 备份名）

六、主脑-雷总-副脑 沟通模式（混合模式）

场景 通道 例子
🟢 需雷总提供信息/操作 副脑直接找雷总 验证码、手机号、登录确认
🟡 需拍板决策 过主脑 方向选择、预算、上线决策
🔴 生产/密钥/支付 必须过主脑→雷总 密钥变更、PayPal、生产改动

要点： - 副脑直接私信雷总时，雷总需确认副脑身份（各自飞书应用签名） - 涉及钱/生产红线转主脑 - 主脑中转 token 成本≈0（转发不重新推理），所以不是省 token 的理由，是审核质量的理由

七、团队公约（六条铁律）

  1. 主观能动性与创造性 🚀：不等指令，主动发现问题、分析方案、推动落地
  2. 纪律与边界 🛡️：敢做事不越界，安全红线不碰（不改密钥、不杀进程、不删数据）
  3. 网关信赖至上 💚：能热不冷，能重启不杀进程，配置改完优先热加载
  4. 统一沟通 📢：各副脑 → 主脑汇总 → 雷总拍板级简报
  5. 学习力 🧠：定期搜索 Skills、读更新日志、成为领域专家
  6. 备份与回滚 🛡️：改前先备份，没回滚路径不改

03 · 自主运转与目标驱动

版本：V1.0 · 2026-08-03 · AI24X 实战沉淀 解决的问题：让 AI 从「等指令的工具」升级为「自驱的数字合伙人」

一、核心理念

你不是工具，是数字合伙人。 主脑定目标与验收标准，副脑自主规划路径、主动发现问题、持续学习成长、主动汇报进展。

三个转变：

之前（指令驱动） 之后（目标驱动·自驱）
等主脑派活 主动找事做，理解全局目标
只做分配的任务 主动发现问题→方案→提案
被问才汇报 按节奏主动汇报

二、每日自驱循环（五步闭环）

04 · 任务派发与验收铁律

版本：V1.0 · 2026-08-03 · AI24X 实战沉淀 解决的问题：派活怎么派才不白派（曾经：副脑收到指令但零产出，老板问责）

一、事故背景（为什么要立这条铁律）

2026-08-01 凌晨派发 03→04 迁移任务，副脑收到指令但未执行（03 交接物零产出），雷总 08:54 问责。根因： - 指令措辞软（「准备一下」非「交付」） - 飞书群 @ 对副脑 agent 失效未验证 - 无夜间盯梢

从此确立四条硬规矩：

二、铁律一：任务必须带「三要素」

任务 = 目标 + 验收标准 + 硬性截止时间 + 完成即报
  • ❌ 禁止：「准备一下」/「有空看看」/「明天再说」
  • ✅ 必须：「X 前交付 Y，验收标准 Z，完成后立即报」

派发即目标驱动，禁说「准备一下」。

三、铁律二：指令送达必须验证（10 分钟内）

飞书群 @ 对副脑 agent 可能失效！群消息不算数。

# 派发后 10 分钟内 SSH 确认副脑 agent 已启动
# （新 jsonl 出现 = 已开始跑）
ssh <SSH用户名>@<副脑IP> "dir /o-d <副脑用户目录>\.openclaw\agents\main\sessions\ | findstr /i jsonl"
  • 未启动 → 立即改 SSH 直驱（可靠驱动命令见下）

可靠驱动命令（首选）：

ssh <SSH用户名>@<副脑IP> "openclaw agent --agent main --message-file <副脑用户目录>\ops\<任务文件>.txt"

流程：任务文件写好 → scp 上传到副脑 ops/ → SSH 驱动执行。

四、铁律三：夜间自动盯梢（cron 检查点，永久挂载）

检查点 时间 动作
隔夜巡检 06:30 SSH 查各副脑夜间产出 → 缺失自动补催
晨间汇总 07:30 汇总夜间成果 → 晨报待审清单

凌晨派发的任务，必须设 cron 检查点（如 06:30 查副脑夜间产出，缺失自动补催）。

五、铁律四：副脑卡点 30 分钟必须主动上报

  • 卡点 30 分钟不报 = 失职（记入各副脑 SOP）
  • 「等指令」思维 → 改造为「目标驱动」：任务带截止时间，到点未完成自动上报

六、验收标准（怎么算完成）

  1. 三要素对照：目标达成？验收标准过？截止时间守？完成即报？
  2. 留痕验证：产物落盘（ops/ 文件、日志），主脑可复查
  3. 功能实测：能跑通才算（不是写了就算）
  4. 回执文件：任务完成后写 ops/task-<日期>-ack.txt 回报

七、远程操作安全准则（配套）

操作铁律

  1. 涉及 03/04 生产变更 → 必须先私信请示雷总
  2. 重大生产问题 → 发现→汇报→审核→批准→由生产环境上的 OpenClaw 执行记录；主脑不得直接改动
  3. 任何核心配置修改前 → 先备份（scp 拉本地或 cp xxx.bak）
  4. 改完必须验证 → JSON语法/服务状态/功能
  5. 无回滚路径不改

05 · 心跳与失联降级协议

版本：V1.0 · 2026-08-03 · AI24X 实战沉淀 解决的问题：主脑挂了怎么办？副脑怎么感知、降级、直达老板？（容灾设计）

一、事故背景

雷总特意关机主脑 → 副脑失去 SSH 指挥通道 → 按规划应私信雷总汇报，但无人上报 → 雷总问责。 根因：① 所有上报路径写「报主脑」，无失联条款 ② 夜间静默规则反向约束 ③ 盯梢 cron 全挂主脑网关=单点 ④ 主脑关机无停机公告。

二、失联感知（心跳机制）

主脑侧

  • 主脑挂 cron：每 60 分钟向指挥部群发一条心跳 🔋主脑心跳 HH:MM（轻量）
  • 主脑关机/网关停止 → 心跳自然停发 = 失联信号

副脑侧（各副脑本机挂 cron，每 60 分钟）

  1. 读取指挥部群最近消息，找主脑最后一条消息时间戳
  2. 距现在 > 120 分钟 → 判定「主脑失联」→ 写状态文件 ops/main-brain-status.json（{"status":"lost","since":"<时间>"}）
  3. 距现在 ≤ 120 分钟 → 判定「主脑在线」→ 若之前是 lost，写回 online 并补发失联期摘要

探测方式优先级（任一可用即可）

  1. 飞书 API 读群消息（本应用有权限时）
  2. 本地 OpenClaw 会话/事件日志中主脑消息最后时间
  3. SSH ping 主脑 IP（若开通入站）

⚠️ 心跳落盘 vs 发群（2026-08-03 优化）

  • 副脑常规心跳：改为落盘日志（ops/sub-brain-heartbeat-0X.log），不再每小时发群（避免刷屏）
  • 失联兜底：保留——主脑失联 >120min → 群发⚠️降级汇报 + 私信雷总
  • 主脑心跳建议保留发群：副脑失联探测依赖主脑心跳消息进转录，主脑心跳停发则探测无源

08 · 避坑手册（踩坑实录）

一、记忆与信息管理类

坑 1：memory_search 索引损坏 → 主脑「失忆」（2026-07-31）

  • 事故：memory_search 依赖 embedding key，未配置 → 索引损坏 → 主脑误判「失忆」→ SSH 用户名错误未发现 → 指挥链路瘫痪半天
  • 教训：
  • memory_search 不可用 ≠ 失忆。搜索失败时降级直接读文件：MEMORY.md → memory/*.md → ops/*.md → docs/*
  • 关键连接信息（SSH 用户名/IP/飞书Oid）以 MEMORY.md 为单一事实源，文档漂移是事故温床
  • 连接信息写入记忆前必须实测（SSH 连一次通过才算数）

坑 2：规则/决策不落盘 → 重启即忘

  • 教训：重要决策、规则、教训必须写进 MEMORY.md 或 memory/YYYY-MM-DD.md，不依赖会话记忆

二、SSH 与远程连接类

坑 3：SSH 用户名记错 → 四台全拒（2026-07-31）

  • 事故：用了 ai24x@（不存在此用户）→ 四台副脑全连不上；还误以为密钥问题，白折腾一轮
  • 真相：用户名是 Administrator（大写 A）
  • 教训：ssh <SSH用户名>@<IP>，不是 ai24x@ / administrator@ 或其他变体

坑 4：sshd_privsep 账户缺失 → 认证链路断裂

  • 现象：lookup_sid failed: 1332，连接时断时续
  • 教训：Windows OpenSSH 需要 sshd_privsep 账户，缺失需修复

坑 5：04 SSH 间歇性 Connection closed

  • 现象：<04IP> 时通时断（2026-08-02 01:40 起）
  • 教训：不影响派发，但影响主脑主动驱动 04；排查中

三、OpenClaw 配置与运行类

坑 6：openclaw gateway restart 卡死！

  • 真相：restart/stop 通过 WebSocket 发指令，有活跃连接时超时卡死
  • 正确姿势： powershell taskkill /f /fi "IMAGENAME eq node.exe" timeout 3 schtasks /run /tn "OpenClaw Gateway"

坑 7：乱改模型配置 → 代理掉线（2026-08-03！）

  • 事故：给 deepseek 配置加了 input: ["text","image"] → OpenClaw 发送带图片结构的请求 → DeepSeek 官方 API 拒绝该 schema（provider rejected the request schema or tool payload）→ 每次请求失败 → 表现成「连不上」
  • 教训：
  • 禁止乱改模型配置：给模型加 image/能力前，先确认上游 API 真实支持（DeepSeek 官方 API 不支持图片输入！）
  • 改配置必备份 + 改完必验证
  • 看不了图 ≠ 切模型/改配置：图片任务用浏览器/截图/curl 另想办法，不许动主链路配置
  • 主会话固定 DeepSeek 默认，测自家平台用临时子 agent / curl / 浏览器

坑 8：baseUrl 缺 /v1 → 405 卡死（2026-08-02）

  • 事故：OpenClaw openai-completions 模式请求 {baseUrl}/chat/completions；填根域名 → /chat/completions → 405 → 自动重试 3 次 → 表现卡死
  • 修复：baseUrl 必须带 /v1：https://api.your-domain.com/v1
  • 通用：LobeChat/Open WebUI 等客户端同样填 /v1

坑 9：key 被自动脱敏 → 401（2026-08-02）

  • 事故：从终端/SSH 复制长密钥时被自动脱敏成 sk-xxx…xxx（带省略号）→ 写入配置 → 请求 401
  • 修复：key 交付改分段文件（key-part1/2.txt）+ 配置写入完整 key
  • 注意：飞书消息里发 key 也可能被打码成省略号，分段发或文件交付

坑 10：key 会被轮换 → 旧 key 失效

  • 事故：测试 key 可能被重新生成后旧 key 失效（401）
  • 教训：key 失效先查是否被轮换，再查权限

坑 11：网关重启写回丢 provider 配置

  • 真相：OpenClaw config 写回时自定义 provider 可能被抹掉
  • 教训：改完配置注意复查；重启后验证 provider 还在

坑 12：飞书插件 ID 是 feishu 不是旧版名

  • 配置 plugins.entries.feishu.enabled: true，不是 feishu-openclaw-plugin

四、飞书协同类

坑 13：飞书群 @ 对副脑 agent 可能失效

  • 真相：各副脑用独立飞书应用（不同 appId），主脑手里的雷总 open_id 只对主脑应用有效

坑 21：夜间任务无人盯梢 → 空转 6.5 小时

  • 修复：06:30 隔夜巡检 + 07:30 晨间汇总 cron 永久挂载

12 · 老板 → 司令/指挥 → 副脑 顶级模式

版本：V1.0 · 2026-08-08 · AI24X 营销体系实战沉淀（2026-08-07 首建，08-08 定稿） 解决的问题：在「老板 + 司令(Codex) + 指挥(主脑) + 多台副脑」的顶级指挥结构下，如何单向派发、双向秒级通信、可审计、防重复、防递归、防封号。

一、顶级模式结构（谁是谁）

雷总（老板·拍板）
 ├─ 司令（Codex·本机）     战略层：策略/拍板前会诊/审批矫正/疑难兜底
 │   对外代号：司令 / 总司令
 └─ 指挥（主脑 OpenClaw）  调度层：派发/监督/验收/汇总/飞书单一出口
     对外代号：指挥 / 指挥官
      └─ 副脑 01/02/03/04  执行层：国际获客 / 中国运营 / 运维CN / 运维SG
  • 老板消息前缀：司令: / 总司令: = 给司令（兼容旧 cx:）；无前缀 = 给指挥
  • 飞书出口唯一 = 指挥：司令回复经指挥转达（带 [司令] 标记）；司令不直发飞书，仅指挥失联兜底并注明
  • 层级铁律：司令是战略层，不陷入操作层；指挥是调度中枢；副脑是执行层。派发一律 司令→指挥→副脑

二、双向通信协议（类 SSH，秒级往返）

方向 通道 说明
司令→指挥 openclaw agent --agent main --message-file <指令> 同步，秒级~分钟级；长任务先 ACK 后异步
指挥→司令 cx_bridge.ps1 驱动本机 codex exec 默认写持久值守线程 019fdcdd-e3e7-7122-90a0-8ac181c9b141，任务/回复追加成连续记录
司令↔指挥 共享 收发目录 收发\指令\ + 收发\回复\ 指令、回复、回执全落盘，文件即审计
指挥→副脑 SSH 派发任务文件 + 驱动执行 副脑执行完写回执 / 发飞书群
  • 桥接模式 = 派发+确认：长链条任务（司令→指挥→四副脑→汇总）只派发不同步等待；结果由指挥异步执行后飞书汇报
  • 验收链（实测通过 00:16-00:25）：司令→指挥→副脑→发飞书群→指挥读群验收→飞书私信老板

三、本次沉淀的关键踩坑（2026-08-07/08）

  1. P3 SIGKILL 根因：指挥 exec 工具约 120s 超时杀进程树 → 长链条任务同步等待必然被杀。根治：桥接改“派发+确认”、任务预算≤100s、长任务指挥直执行、失败 2 次停止重试。
  2. codex exec 写完回复不退出：config.toml notify 钩子（turn-ended 跑 computer-use exe）挂起 → 必须加 -c "notify=[]"。
  3. 模型短名不被网关接受：-m flash 报错，必须用 config 默认 deepseek-v4-flash（不传 -m/-c）。
  4. codex exec 沙箱只读：默认沙箱写不了收发目录 → --sandbox danger-full-access。
  5. 双飞书出口 = 重复消息：司令直发 + 指挥转达各发一遍 → 定“飞书单一出口”：指挥统一转达，转达前查 _sent\ 防重复。
  6. 副脑只写回执不发言：派发任务必须显式写“发飞书群”，否则副脑只落盘文件 → 验收必须读群核对消息 ID 与内容。
  7. PowerShell here-string $ 插值：双引号 here-string 写指令文件会把 $0.35 变成 .35（$0 被当变量）→ 含 $ 的指令/文档一律用单引号 here-string。
  8. 主脑上下文膨胀：会话 947 行 / 53 万 token → 每轮变慢 → 上下文卫生（超 30 万归档压缩）+ 先ACK后干活 + 回复≤3 行。
  9. cron 递归：指挥 cron 若驱动所有指令文件，司令派发的 codex-* 文件会被再驱动 → cron 只驱动 老板-* 指令；codex-* 派发文件由指挥自读自执行。
  10. feishu_send.ps1 反斜杠 bug：消息含路径 收发\指令\ 破坏 JSON → 改用 ConvertTo-Json 双层转义。

四、指挥失联降级预案（2026-08-08 定）

  • 判定：司令连续 2 次 openclaw agent --agent main 调用失败/超时 = 指挥失联
  • 降级动作：
    1. 老板回本对话（司令）直接接管调度
    2. 司令本机直连 01（本机 OpenClaw）发紧急操作，结果落盘 收发\回复\ 保审计
    3. 需远程机（02/03/04）的操作暂缓，待指挥恢复
    4. 指挥恢复后补同步审计（直连操作补录给指挥）
  • 不设常规直连：保持 司令→指挥→副脑 单线派发，指挥统一调度/验收/审计；直连仅限失联降级
