## §0 项目边界与子项目关系

### 0.1 什么是根项目

**AI24X 根项目** = 全平台共享的底层基础设施，定位为"多模型 API 聚合与交易平台"。根项目只负责：

| 根项目负责 | 根项目不负责 |
|-----------|-------------|
| 用户注册/登录/认证（JWT + API Key） | AI 行情官 K 线信号算法 |
| 模型路由 & 容错（多 Provider 切换） | 山海渔钓鱼游戏逻辑 |
| 计费 & Token 消耗统计 | 子项目各自的业务数据库 |
| 共享 Key 池 & C2C 分成 | 子项目各自的前端 UI |
| 管理后台（用户/Key/日志） | 子项目各自的行业逻辑 |
| 支付（微信/支付宝/PayPal） | — |
| 推荐返利（二级） | — |

### 0.2 子项目关系


## §2 用户体系

### 2.1 三级用户

| 等级 | 获取方式 | 每日 Token 配额 | 可选模型 | 优先级 |
|------|----------|----------------|----------|--------|
| **FREE** | 注册即得 | 10,000 tokens/天 | DS-V4-Flash, GLM-4-Flash, 豆包Lite | 低 |
| **VIP** | ¥19.9/月 | 500,000 tokens/天 | + V4-Pro, 豆包Pro, Qwen-Max | 中 |
| **DEV** | ¥49.9/月 或 BYOK | 2,000,000 tokens/天 | + 全部模型 + 优先调度 | 高 |

### 2.2 模型分级

```
L0（试用）: DS-V4-Flash（免费引流），GLM-4-Flash，豆包Lite
L1（标准）: DS-V4-Pro，豆包Pro，Qwen-Max
L2（旗舰）: GPT-4o，Claude 3.5 Sonnet，Gemini 2.0（二期）
```

### 2.3 配额检查流程

```python
# 伪代码：请求入口
user = authenticate(api_key)
model = resolve_model(request.model)
level = user.level  # FREE / VIP / DEV

# 1. 等级模型白名单
if model not in LEVEL_MODEL_MAP[level]:
    return 403 "模型不可用，升级VIP解锁"

# 2. 日配额
today_usage = get_today_usage(user.id)
if today_usage + estimated_tokens > LEVEL_QUOTA[level]:
    return 429 "今日配额已用完"

# 3. 余额（VIP/DEV 预付费）
if level != FREE and user.balance <= 0:
    return 402 "余额不足"

# 4. 通过，进入路由
```

## §3 容错链与路由

### 3.1 两套容错链

**FREE 链路：**
```
请求 → SiliconFlow(DS-V4-Flash)  ──失败──→ DeepSeek直连(V4-Flash) ──失败──→ 豆包Lite
          │ 超时 3s / 429 / 5xx               │ 超时 3s / 429 / 5xx          │
          └──成功──→ 返回                       └──成功──→ 返回               └──成功──→ 返回
                                                                                 │
                                                                             └──全部失败──→ 返回 503
```

**VIP 链路：**
```
请求 → DeepSeek直连(V4-Flash) ──失败──→ DeepSeek(V4-Pro) ──失败──→ 豆包Pro
          │ 超时 5s / 429 / 5xx          │ 超时 5s / 429 / 5xx       │
          └──成功──→ 返回                  └──成功──→ 返回            └──成功──→ 返回
                                                                            │
                                                                        └──全部失败──→ 返回 503
```

### 3.2 Provider 配置表

| Provider | 模型 | 定价(输入/输出，元/百万token) | 超时 | 用途 |
|----------|------|------------------------------|------|------|
| SiliconFlow | DS-V4-Flash | ¥0.5 / ¥1.0 | 3s | FREE 首选 |
| DeepSeek 直连 | V4-Flash | ¥1.0 / ¥2.0 | 3s(FREE) 5s(VIP) | FREE次选 / VIP首选 |
| DeepSeek 直连 | V4-Pro | ¥2.0 / ¥4.0 | 5s | VIP 次选 |
| 豆包（火山） | Lite | ¥0.8 / ¥2.0 | 3s | FREE 兜底 |
| 豆包（火山） | Pro | ¥3.0 / ¥9.0 | 5s | VIP 兜底 |
| 智谱 GLM | GLM-4-Flash | ¥0.0（免费额度） | 3s | L0 引流 |

### 3.3 熔断规则

| 条件 | 动作 | 恢复条件 |
|------|------|----------|
| 连续失败 ≥ 5 次 / 1分钟 | 该 Provider 熔断 60s | 60s 后放 1 个探测请求 |
| 5xx 率 ≥ 30% / 5分钟 | 该 Provider 熔断 300s | 300s 后放 1 个探测请求 |
| 429 率 ≥ 50% / 1分钟 | 自动降权，延后调度 | 恢复后逐步放量 |

## §4 共享 Key 池

### 4.1 为什么需要

用户或合作伙伴可将自己的 API Key 贡献给平台 Key 池，平台统一调度使用，贡献者获得分成。这解决了三个问题：
1. 平台不需要自己大量垫资采购 Key
2. 贡献者闲置 Key 产生收益
3. 容错能力更强（Key 池越大，单 Key 失效影响越小）

### 4.2 数据模型

```sql
-- Key 池主表
CREATE TABLE key_pool (
    id            UUID PRIMARY KEY,
    contributor_id UUID NOT NULL REFERENCES users(id),
    provider      VARCHAR(32) NOT NULL,      -- siliconflow / deepseek / doubao
    model_family  VARCHAR(64) NOT NULL,      -- DS-V4-Flash / GLM-4-Flash
    api_key_enc   TEXT NOT NULL,             -- AES-256-GCM 加密后的 Key
    status        VARCHAR(16) DEFAULT 'active', -- active / drained / revoked
    daily_limit   BIGINT DEFAULT 0,           -- 0 = 无限制
    total_used    BIGINT DEFAULT 0,
    error_count   INT DEFAULT 0,
    last_error_at TIMESTAMP,
    last_used_at  TIMESTAMP,
    created_at    TIMESTAMP DEFAULT NOW(),
    updated_at    TIMESTAMP DEFAULT NOW()
);

-- Key 贡献者收益
CREATE TABLE key_contribution_earnings (
    id             UUID PRIMARY KEY,
    contributor_id UUID NOT NULL,
    key_pool_id    UUID NOT NULL,
    date           DATE NOT NULL,
    tokens_used    BIGINT DEFAULT 0,
    cost_to_platform DECIMAL(12,4) DEFAULT 0,  -- 平台实际支出
    revenue        DECIMAL(12,4) DEFAULT 0,     -- 贡献者分成
    settled        BOOLEAN DEFAULT FALSE,
    UNIQUE(contributor_id, key_pool_id, date)
);
```

### 4.3 贡献流程

```
1. 用户 → 控制台 "贡献我的 Key"
2. 选择 Provider + 模型 → 粘贴 Key → 平台验证(发一个最小请求)
3. 验证通过 → Key 加密存储 → 进入 active 池
4. 贡献者设置日上限（可选）
5. 平台实时统计消耗 → T+1 结算分成
```

### 4.4 调度算法

```python
# 从 Key 池中选择最优 Key
def select_key(provider: str, model: str) -> KeyPool:
    candidates = KeyPool.query.filter(
        KeyPool.provider == provider,
        KeyPool.model_family == model,
        KeyPool.status == 'active',
        KeyPool.error_count < 5
    ).order_by(
        KeyPool.total_used.asc(),      # 优先用消耗少的（均衡）
        KeyPool.last_used_at.asc()     # 次选最久没用过的
    ).limit(1)
    return candidates.first()
```

### 4.5 激励机制

| 条件 | 分成比例 |
|------|----------|
| 基础分成（默认） | Key 消耗成本的 **30%** 返给贡献者 |
| 优质 Key（可用率 ≥ 99%） | 提升至 **35%** |
| 高频 Key（日调用 ≥ 1000 次） | 提升至 **40%** |
| 平台抽成 | Key 消耗成本的 **20%**（平台运营费） |
| 净平台留存 | ≈ 50%（扣除分成后） |

> 示例：用户贡献 SiliconFlow Key，日消耗 100 元成本。平台向终端收费 130 元。贡献者得 30 元（30%×100）。平台得 130-100-30 = 0 元（需定价覆盖运营）→ **建议终端价 = 成本 × 1.5 以上**。

### 4.6 安全措施

| 措施 | 说明 |
|------|------|
| AES-256-GCM 加密 | Key 在数据库中以密文存储，密钥仅存在于 KMS 或环境变量 |
| 最小请求验证 | 贡献时平台发 5-token 测试请求，既验证有效性，又不浪费额度 |
| 贡献者可随时撤销 | `status = 'revoked'`，立即从调度池移除 |
| 日上限保护 | 贡献者可设日 token 上限，防止被刷爆 |
| 异常熔断 | 连续 5 次上游拒绝 → 自动 `error` 状态 → 通知贡献者 |

## §6 请求全流程

### 6.1 完整流程图

```
用户请求 POST /v1/chat/run
        │
   ┌────▼─────────────────────┐
   │ 1. 鉴权                   │  JWT Token 或 API Key
   │    → 提取 user_id, level  │  失败 → 401
   └────┬─────────────────────┘
        │
   ┌────▼─────────────────────┐
   │ 2. 模型解析               │  model_alias → actual_model
   │    → 检查白名单           │  不在白名单 → 403 "升级VIP"
   └────┬─────────────────────┘
        │
   ┌────▼─────────────────────┐
   │ 3. 配额检查               │  today_usage + estimated ≤ quota
   │    → 余额检查(VIP/DEV)    │  超配额 → 429 / 余额不足 → 402
   └────┬─────────────────────┘
        │
   ┌────▼─────────────────────┐
   │ 4. Key 调度               │  L1(共享池) → L2(认证供给) → L3(BYOK)
   │    → select_key()         │  无可用 Key → 503
   └────┬─────────────────────┘
        │
   ┌────▼─────────────────────┐
   │ 5. 上游调用               │  POST provider_url  (with timeout)
   │    → stream 处理          │
   └────┬─────────────────────┘
        │
   ┌────▼─────────────────────┐
   │ 6. 容错处理               │  超时/429/5xx → next provider in chain
   │    → 熔断检查             │  全部失败 → 503
   └────┬─────────────────────┘
        │ 成功
   ┌────▼─────────────────────┐
   │ 7. 计费 + 日志            │  写入 token_usage + 更新 key_pool
   │    → 返回响应             │  审计日志追加
   └──────────────────────────┘
```

### 6.2 关键中间件

| 中间件 | 位置 | 功能 |
|--------|------|------|
| `AuthMiddleware` | 路由前 | JWT/API Key 验证，提取 user |
| `RateLimitMiddleware` | 路由前 | IP/用户维度限流 |
| `BillingMiddleware` | 调用后 | 记录 Token 消耗，更新余额 |
| `AuditMiddleware` | 调用后 | 关键操作日志 |
| `ErrorHandler` | 全局 | 统一异常 → HTTP 状态码 |

### 6.3 请求 ID 全链路追踪

每请求生成 `x-request-id`（UUID v4），贯穿：
- 入口日志 → 路由决策 → Provider 调用 → 响应返回
- 写入 `token_usage.request_id`
- 管理员可按 request_id 回溯完整链路

## §8 数据模型（统一版）

### 8.1 与现有 schema 的关系

**现状**：`db/schema.sql`（10 表规划级）与 `api/models.py`（5 个 SQLAlchemy 模型）口径不一致。

**统一方案**：以下 8 张核心表为根项目基础，替换现有两份分散定义：

| # | 表名 | 说明 | 对应旧表 |
|---|------|------|----------|
| 1 | `users` | 用户主表（合并 AuthUser） | `api/models.py: User + AuthUser` |
| 2 | `api_keys` | API Key（用户自用+调用用） | `db/schema.sql: api_keys` |
| 3 | `model_routing` | 模型路由配置 | 新增（替代 model_configs） |
| 4 | `key_pool` | 共享 Key 池 | 新增 |
| 5 | `token_usage` | Token 消耗明细 | `db/schema.sql: token_usage` |
| 6 | `billing_records` | 计费记录 | `db/schema.sql: billing_records` |
| 7 | `referral_records` | 推荐关系 | 新增 |
| 8 | `audit_logs` | 审计日志 | `db/schema.sql: audit_logs` |

### 8.2 核心 DDL

```sql
-- ===================== 1. 用户表 =====================
CREATE TABLE users (

    updated_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 2. API Key 表 =====================
CREATE TABLE api_keys (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    api_key_prefix  VARCHAR(12) NOT NULL,            -- 前 8 位明文，用于控制台展示
    name            VARCHAR(64),
    permissions     JSONB DEFAULT '["chat"]',
    rate_limit      INT DEFAULT 60,                  -- 次/分钟
    total_calls     BIGINT DEFAULT 0,
    is_active       BOOLEAN DEFAULT TRUE,
    created_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 3. 模型路由配置 =====================
CREATE TABLE model_routing (
    id              SERIAL PRIMARY KEY,

    provider        VARCHAR(32) NOT NULL,          -- siliconflow / deepseek / doubao
    actual_model    VARCHAR(64) NOT NULL,           -- 上游真实 model 字符串
    api_endpoint    VARCHAR(256) NOT NULL,
    api_key_ref     VARCHAR(128),                   -- KMS 引用或加密值
    input_price     DECIMAL(10,6) NOT NULL,         -- 元/百万 token
    output_price    DECIMAL(10,6) NOT NULL,
    min_level       VARCHAR(8) DEFAULT 'FREE',      -- 最低用户等级
    priority        INT DEFAULT 100,                -- 同级内优先级，越小越高
    timeout_ms      INT DEFAULT 5000,
    max_retries     INT DEFAULT 2,
    is_active       BOOLEAN DEFAULT TRUE
);

-- ===================== 4. 共享 Key 池 =====================
CREATE TABLE key_pool (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contributor_id  UUID NOT NULL REFERENCES users(id),
    provider        VARCHAR(32) NOT NULL,
    model_family    VARCHAR(64) NOT NULL,
    api_key_enc     TEXT NOT NULL,                   -- AES-256-GCM 加密
    status          VARCHAR(16) DEFAULT 'active',    -- active / drained / error / revoked
    daily_limit     BIGINT DEFAULT 0,
    total_used      BIGINT DEFAULT 0,
    error_count     INT DEFAULT 0,
    last_error_at   TIMESTAMP,
    last_used_at    TIMESTAMP,
    created_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 5. Token 消耗 =====================
CREATE TABLE token_usage (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(id),
    api_key_id      UUID REFERENCES api_keys(id),
    request_id      UUID NOT NULL,                   -- 全链路追踪
    model_alias     VARCHAR(64) NOT NULL,
    provider        VARCHAR(32) NOT NULL,
    actual_model    VARCHAR(64) NOT NULL,
    key_pool_id     UUID REFERENCES key_pool(id),    -- 若用共享池
    input_tokens    INT DEFAULT 0,
    output_tokens   INT DEFAULT 0,
    cost            DECIMAL(12,6) DEFAULT 0,         -- 平台成本
    charge          DECIMAL(12,6) DEFAULT 0,         -- 用户扣费
    latency_ms      INT,
    created_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 6. 计费记录 =====================
CREATE TABLE billing_records (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(id),
    type            VARCHAR(16) NOT NULL,             -- recharge / consume / refund / withdraw
    amount          DECIMAL(12,4) NOT NULL,
    balance_after   DECIMAL(12,4) NOT NULL,
    payment_method  VARCHAR(32),                      -- wechat / alipay / paypal
    transaction_id  VARCHAR(128),
    status          VARCHAR(16) DEFAULT 'completed',
    created_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 7. 推荐关系 =====================
CREATE TABLE referral_records (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    inviter_id      UUID NOT NULL REFERENCES users(id),
    invitee_id      UUID NOT NULL REFERENCES users(id),
    level           INT DEFAULT 1,                    -- 1=直接, 2=间接
    invitee_first_charge BOOLEAN DEFAULT FALSE,
    commission      DECIMAL(12,4) DEFAULT 0,
    settled         BOOLEAN DEFAULT FALSE,
    created_at      TIMESTAMP DEFAULT NOW()
);

-- ===================== 8. 审计日志 =====================
CREATE TABLE audit_logs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID REFERENCES users(id),
    action          VARCHAR(64) NOT NULL,             -- chat.call / keypool.contribute / admin.force
    resource_type   VARCHAR(32),
    resource_id     VARCHAR(64),
    request_id      UUID,
    ip_address      INET,
    details         JSONB,
    created_at      TIMESTAMP DEFAULT NOW()
);

-- 索引
CREATE INDEX idx_token_usage_user_date ON token_usage(user_id, created_at);
CREATE INDEX idx_token_usage_request ON token_usage(request_id);
CREATE INDEX idx_key_pool_status ON key_pool(status, provider, model_family);
CREATE INDEX idx_billing_user ON billing_records(user_id, created_at);
CREATE INDEX idx_referral_inviter ON referral_records(inviter_id);
```

## §10 成本估算与盈利模型

### 10.1 基础设施成本（月）

| 项目 | 规格 | 月费(¥) | 说明 |
|------|------|---------|------|
| 副脑01（上海 4C8G） | 已有 | ~200 | API Gateway + Router |
| 副脑02（上海 2C8G） | 已有 | ~100 | FREE 代理 + 静态站 |

| 域名+CDN | — | ~50 | ai24x.com |
| **合计** | | **~¥500** | |

### 10.2 上游模型成本（百人规模）

假设：100 注册用户，10% 日活，日均每人消耗 20,000 tokens

| 用户群 | 人数 | 日均 Token | Provider | 单价(元/百万) | 日成本(¥) | 月成本(¥) |
|--------|------|-----------|----------|--------------|----------|----------|
| FREE | 80 | 5,000 | SiliconFlow V4-Flash | ¥0.5+1.0 | ~1.5 | 45 |
| FREE 溢出 | 20 | 5,000 | 豆包 Lite | ¥0.8+2.0 | ~2.8 | 84 |
| VIP | 10 | 50,000 | DS V4-Pro | ¥2.0+4.0 | ~30 | 900 |
| **合计** | | | | | **~¥34/天** | **~¥1,029/月** |

实际 FREE 用户消耗应远低于此估算（大多数注册不用），且 L0 模型有免费额度可用。

### 10.3 收入模型

| 等级 | 定价 | 月成本(Token) | 毛利 | 目标转化率 |
|------|------|--------------|------|-----------|
| FREE | ¥0 | ¥1.3/人 | -¥1.3 | — |
| VIP | ¥19.9/月 | ¥90/人 | -¥70（需优化） | 5-10% |
| DEV | ¥49.9/月 | ¥150/人 | -¥100（需优化） | 1-3% |

> **⚠️ 当前模型 VIP 是亏损的**，原因：VIP 给的 50 万/天 token 太多，且 V4-Pro 单价高。
>
> **修正方案**：
> 1. VIP 日配额降为 **100,000/天**（够日常使用）
> 2. VIP 首选模型用更便宜的 V4-Flash，Pro 作为溢出
> 3. 引入**按量付费**作为补充：¥0.01/千 token，用多少付多少

**修正后盈利模型**：

| 方案 | 定价 | 日均 Token 成本 | 月成本 | 毛利 |
|------|------|----------------|--------|------|
| VIP 订阅 | ¥19.9/月 | 100,000 × V4-Flash ¥1.0 | ~¥6 | **+¥13.9** |
| VIP 按量 | ¥0.01/千 token | 100K × 0.01 | ¥30/月（用户付） | **+¥24** |
| DEV 订阅 | ¥49.9/月 | 300,000 × 混合 | ~¥45 | **+¥4.9** |
| DEV 按量 | ¥0.008/千 token | 300K × 0.008 | ¥72/月（用户付） | **+¥27** |

### 10.4 盈亏平衡点

```
月固定成本：¥500（服务器）+ ¥50（域名）= ¥550
平台费率：~20%（支付+运营损耗）

需月收入 ≥ ¥550 / 0.8 = ¥688

VIP 订阅 ¥19.9 × 35 人 = ¥697 → 盈亏平衡
或 VIP ¥19.9 × 20 人 + DEV ¥49.9 × 4 人 = ¥598（接近平衡）
或 FREE 引流 + 推荐返利被消费抵扣 → 拉长到 3 个月实现盈亏平衡
```

## §11 安全风控

### 11.1 防刷

| 措施 | 实现 |
|------|------|
| 新用户日配额极低 | FREE 首 7 天仅 1,000 token/天 |
| IP 频率限制 | 同一 IP 每分钟 ≤ 10 请求 |
| 行为检测 | 连续短文本 + 极高频率 → 标记 |
| 验证码 | 异常触发 → 滑块验证码 |
| C2C Key 日上限 | 贡献者自设上限，防爆刷 |

### 11.2 密钥安全

| 措施 | 实现 |
|------|------|
| 加密存储 | AES-256-GCM，密钥仅 KMS |
| 预发布隔离 | 不使用生产 Key |
| 轮换机制 | 管理员可批量轮换 Key |
| 脱敏展示 | 控制台显示 `sk-****xxxx` |

### 11.3 熔断与降级

| 场景 | 动作 |
|------|------|
| Provider 连续失败 | 自动熔断 60-300s，见 §3.3 |
| 全链路失败 | 返回 503 + "服务繁忙，请稍后重试" |
| DB 连接失败 | 返回 503，不影响已建立的静态站 |

### 11.4 错误脱敏

```
外部返回：{ "error": "service_unavailable", "message": "服务繁忙" }
内部日志：{ "error": "deepseek timeout 5s", "trace": "..." }
```

## §12 子项目继承规范

### 12.1 继承原则

| 根项目能力 | 子项目继承方式 | 示例 |
|-----------|---------------|------|
| **用户认证** (JWT) | 共享 `users` 表 + 同 JWT Secret | A1 行情官用同一套登录态 |
| **API Key** | 子项目可颁发子域 API Key | 免重复开发 |
| **计费系统** | 可选继承，独立计费则自建 | Fisher 独立计费 |
| **推荐返利** | 贡献池可选接入 | A1 分享卡片带邀请码→返利 |
| **管理后台** | 根项目提供 `/admin/*`，子项目不重复造 | — |
| **前端主题** | 共享 CSS 变量 + shell 组件 | 统一品牌视觉 |

### 12.2 不继承的内容

| 子项目 | 不可继承 | 原因 |
|--------|---------|------|
| 所有子项目 | 业务数据库 | 根项目不关心子项目业务 |
| A1 行情官 | 信号算法、同花顺公式 | 业务特有 |
| Fisher | 游戏逻辑、微信支付 | 业务特有 |

### 12.3 新子项目接入清单

1. 在 `p/` 下创建目录
2. 编写 `README.md`，注明依赖的根项目能力
3. 如需要用户认证 → 对接根项目 JWT（同 Secret）
4. 如需要计费 → 声明是「共享计费」还是「独立计费」
5. 如需要 API 端点 → 在根网关配置代理路由 `/v1/{project}/* → p/{project}/api`
6. 前端页面 → 使用根项目 `shell.js` 挂载统一页头页脚
