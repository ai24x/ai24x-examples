# 《山海渔》Fisher 子项目 — 架构与落地汇总（优化版）

> 本文档汇总本会话内与负责人对齐后的技术路线：**原生小程序 + 自建 API 真源 + PostgreSQL + 管理端分域**；并说明与主站 `api/`、子站 `p/a`（AI 行情官）的**统一 / 不统一**边界。  
> 可复用的工程经验见文末「从 AI 行情官复制的清单」，对应仓库内真实路径。

**关联**：产品策划完整版见 [`产品规划-山海渔-完整版-v1.0.md`](./产品规划-山海渔-完整版-v1.0.md)；默认身份与真源边界见仓库根目录 **`memory/decisions/DEC-0009-山海渔-Fisher身份默认独立与真源边界.md`**。

## 1. 目标与边界

| 维度 | 结论 |
|------|------|
| 产品 | 微信小程序优先；**12～24 个月内**上 H5 / App；经济、库存、冷却、排行等 **服务端真源**。 |
| 客户端 | **微信原生**（WXML / WXSS / JS）；动效以 **CSS + 少量 canvas** 为主，`transform` 优先。 |
| 后端 | **自建**（建议 FastAPI + PostgreSQL），与 `p/a` 同类的「子项目自带 `api/server`」形态。 |
| 微信云开发 | **可选**：仅作静态托管、推送、早期实验；**不作为**金币/渔获/交易的长期唯一真源。 |
| 多端（Taro 等） | **不提前上**；待 H5/App 与小程序 **同周迭代**、UI 复用收益明确再评估。 |

## 2. 域名与 TLS（推荐「扁平二级子域」+ 一张通配符证书）

**原因**：`*.ai24x.com` 只覆盖一层子域；`api.fisher.ai24x.com` 这类三级主机名需要额外 `*.fisher.ai24x.com` 或 SAN，运维与证书成本更高。

| 用途 | 推荐主机名 | 说明 |
|------|------------|------|
| 产品 / H5 门面 | `fisher.ai24x.com` | 落地页、活动、分享打开页。 |
| 玩家 API（真源） | `fisher-api.ai24x.com` | 小程序 / 未来 H5 / App 共用；限流、WAF、版本 `/v1`。 |
| 管理后台 | `fisher-admin.ai24x.com` | 与玩家流量隔离；强密钥、可选 IP 白名单、审计。 |
| 证书 | `*.ai24x.com`（DNS-01） | 同时覆盖上述三个主机名。 |

小程序后台需将 **`https://fisher-api.ai24x.com`**（及若用到的 WebSocket 域）加入 **request 合法域名**。

## 4. 真源边界（不可回头线）

**必须只在 `fisher-api` 内完成并落库：**

- 登录态与用户主档（至少 `openid` / `unionid`、内部 `user_id`）
- 抛竿冷却、体力/竿次、钓获随机与校验
- 金币 / 积分增减、仓库、出售、市价快照与交易流水
- 排行榜写入、风控开关（封号、禁言）

**小程序端只做：**

- 动效、弱缓存、`wx.request` 调用、失败重试与展示

## 5. 与主站 / AI 行情官是否要「统一」？（务必确认的决策）

### 5.1 和子站 `p/a`（AI 行情官）一样要统一的部分 — **仅当你选择「全站一个账号」时**

行情官与主站的统一方式见仓库已定稿：`memory/decisions/DEC-0007-身份真源-api与行情官认票.md`。核心是：

- 终端用户真源在 **`api/`**（`auth_users` 等）
- JWT 由 **`api/`** 用 `SECRET_KEY` 签发
- 子站配置 **`AI24X_IDENTITY_API_BASE`**、**`AI24X_JWT_SECRET` 与主站 `SECRET_KEY` 一致**、**`AI24X_SMS_INTERNAL_KEY` 与主站 `SMS_INTERNAL_KEY` 一致**（服务端代理短信等）

**若《山海渔》也要「登录一次，全 AI24X 产品认同一用户」**：建议采用**同一套身份契约**：

- Fisher 后端在验票后，用平台 `sub`（用户 id）作为 **跨产品唯一键**，在本库建 `fisher_users` 或影子表，**游戏资产仍放在 Fisher 库**，不要写进主站 `api/` 的业务表。
- 短信 / 邮箱 OTP、密码重置等：**复用主站 `api/v1/auth/*`**，避免重复造轮子与安全分叉。

### 5.2 建议「不要和主站绑死」的部分 — **默认推荐**

- **游戏经济、渔市、背包、赛季数据**：**始终在 Fisher 自建库**；主站 `api/` 不承载游戏数值真源。
- **游戏管理后台密钥**：**独立**于行情官的 `AI24X_ADMIN_KEY`（不同子域、不同进程、不同 `.env`）。

### 5.3 一句话决策表

| 诉求 | 建议 |
|------|------|
| 只要微信里玩，账号即小程序用户 | **不强制**对接主站 JWT；Fisher-api 自己做 `code2session` + 会话即可。 |
| www / 行情官 / 游戏共用一个「AI24X 账号」 | **统一身份**：对接 `api/` JWT + `IDENTITY_API_BASE`（与 DEC-0007 同模式）；游戏数据仍在 Fisher-api。 |
| 支付 / 会员与主站打通 | 单独定产品契约；技术上前置 **同一 user_id** 会省事很多。 |

**若负责人选定「统一身份」**，建议在 `memory/decisions/` 另起一条 **DEC-xxxx《山海渔-身份与主站关系》**，避免口头口径漂移。

## 7. 阶段里程碑（与产品阶段对齐的工程版）

1. **M0（1～2 周）**：`fisher-api` 最小接口（profile / catch / sell / rod）、Postgres 表、小程序仅调 API；管理端只读查询或改价格表 JSON。  
2. **M1**：渔市快照、冷却与流水审计；小程序动效全套。  
3. **M2**：H5 门面 `fisher.ai24x.com` 与 API 同用户体系；若选统一身份则接主站 JWT。  
4. **M3**：App（壳或混合）+ 支付 / 合规收口。

## 8. P0 / P1 缺口（工程视角）

**P0**

- API 真源 + Postgres；禁止长期依赖客户端随机金币。
- `user_id` / `unionid` 策略与是否对接主站 JWT 的书面二选一。
- 合法域名、HTTPS、管理端密钥与限流。

**P1**

- 赛季 / 转生数据迁移字段预留。
- 激励广告失败降级与数值表外置版本号。
