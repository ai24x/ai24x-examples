# AI24X 密钥安全规划（讨论版）· 2026-09-06

> **雷总约束（铁律）**  
> 1. 本机电脑里的密钥：**先不管、不清理**  
> 2. Gitee 私库里的密钥：**先不管、不清理**  
> 3. 只盯：**生产环境可被外人扫描/盗用** 的面  
> 4. **禁止随便删钥 / 脱敏替换**；必须 **新钥就绪 → 一一对应验证 → 再换**  
> 5. 否则记不住旧钥、系统瘫痪，损失更大  

本文件只做规划与台账模板，**不执行轮换**。

---

## 1. 两件事分开做（最重要）

| 阶段 | 做什么 | 动密钥吗？ |
|------|--------|------------|
| **A. 护面（优先）** | 堵住扫描/盗用路径：SSRF、DIAG 落盘、Cookie、Admin 双因素、APP_ENV | **不换钥** |
| **B. 轮换（有新钥后再做）** | 按台账一行一行换生产 `.env` / 控制台 | **一一对应换** |

先做 A，系统继续用现有密钥跑。B 永远等你手里有「新钥 + 旧钥对照表」再开。

## 2. 生产可被扫到的风险（与本机/Gitee 无关）

这些是「攻击者不用进你电脑」也能碰的：

| 风险 | 说明 | 先怎么护（不换钥） |
|------|------|-------------------|
| BYOK `base_url` SSRF | 用户把网关指到自己的 URL，可能把 **用户自己的 BYOK 钥** 带出去 | 限制公网 https、禁内网/metadata |
| DIAG 全量 body | 日志/磁盘可能留下用户粘贴的密钥片段 | 关掉 DIAG 落盘（不是删生产 `.env`） |
| SSO Cookie 非 HttpOnly | XSS 可偷登录 JWT（会话，不是支付钥） | Cookie 加 HttpOnly |
| Admin 单因子 | 若生产未开 SMS，扫到/撞到 Admin Key ≈ 后台全开 | 确认 `ADMIN_REQUIRE_SMS=true`（你们 08-23 已有双因素定案） |
| `APP_ENV≠production` | 文档页/弱验签等放大面 | 只核对生产是否 production，不改钥 |

**公开前端 JS / source map：** 目前未见 PayPal/Dodo/Admin 明文。  
**本机 `.env`、Gitee 私库：** 按铁律，本规划 **不纳入清理清单**。

## 3. 密钥分类（便于你记）

### 3.1 平台控制面（动错影响最大）

| 代号 | 名称 | 谁用 | 换错会怎样 |
|------|------|------|------------|
| K1 | `SECRET_KEY` | JWT + API Key 校验 + BYOK 加密派生 | **会话全失效、用户 Key 全验不过、BYOK 密文解不开** → **最后换，单独方案** |
| K2 | `ADMIN_API_KEY` | 管理后台 / core↔open | 后台进不去 |
| K3 | `SMS_INTERNAL_KEY` | 短信/部分管理通道 | 验证码/部分管理挂 |
| K4 | `BILLING_SERVICE_KEY` | open↔core 计费代理 | 充值/套餐代理挂 |
| K5 | `MARKETS_FULFILL_SECRET` | core↔markets | Markets 履约挂 |

### 3.2 支付（控制台 + 生产 env 必须同步）

| 代号 | 名称 | 换错会怎样 |
|------|------|------------|
| P1 | PayPal Client Secret / Webhook ID | 下单/回调失败 |
| P2 | Dodo API Key / Webhook Secret | 下单/自动到账失败 |
| P3 | 微信/支付宝（若生产开） | 国内支付挂 |

### 3.3 上游模型（可逐个换）

| 代号 | 名称 | 换错会怎样 |
|------|------|------------|
| U* | OpenRouter / DeepSeek / TokenLab / Requesty / 硅基 / MiMo… | **只挂该通道**，有 failover 可先切备用再换 |

仓库里若有 `_repro_400.py` 等 **前缀痕迹**：仅标记「**有新钥后再考虑是否与生产同一把**」，**现在不删文件、不脱敏、不轮换**。

### 3.4 用户侧（一般不主动批量换）

- 用户 Hub `sk-…`、用户 BYOK：护 SSRF 即可；除非用户主动重置。  
- 换 `SECRET_KEY` 才会牵连全体用户 Key / BYOK —— 所以 K1 永远最后。

## 4. 一一对应台账模板（建议放 `E:\AI24X\安全凭据\`，勿进 git）

每把钥一行，**旧值只写在你本机台账**，聊天/飞书/指令里只写代号：

| 代号 | 用途 | 生产位置（路径/服务） | 控制台位置 | 旧钥指纹（后4位） | 新钥指纹（后4位） | 新钥就绪 | 双端已写 | 冒烟通过 | 旧钥作废日 | 备注 |
|------|------|----------------------|------------|-------------------|-------------------|----------|----------|----------|------------|------|
| K2 | Admin | 04 `C:\ai24x01\api\.env` + open | — | `…xxxx` | | ☐ | ☐ | ☐ | | 与 K3 不得相同 |
| … | | | | | | | | | | |

规则：

1. **没有「新钥指纹」勾选 → 禁止动生产旧钥**  
2. 换完先冒烟，再在控制台/旧渠道 **停用** 旧钥（不是先删）  
3. 指令与回执 **禁止贴明文**，只报代号 + 后 4 位 + PASS/FAIL

## 5. 推荐顺序（有新钥之后才执行）

```
护面 A 完成（可不换钥）
    ↓
K2 Admin（确认 SMS 双因素已开）
    ↓
K3 SMS（core / open / a1 同日对齐）
    ↓
K4 Billing（两端同换同重启）
    ↓
K5 Markets fulfill
    ↓
P1 / P2 支付（控制台可双活则先加新再切）
    ↓
U* 上游（一次一家，先备用通道）
    ↓
K1 SECRET_KEY（单独窗口：会话失效预案 + BYOK 重加密或用户重填）
```

**绝对不要：** 一天换多把、先清空 `.env`、先脱敏仓库指望以后再找。
