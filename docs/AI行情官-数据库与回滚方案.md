# AI 行情官｜灯塔版（1.01）数据库升级到 PostgreSQL（含回滚方案）

适用范围：`p/a`（AI 行情官｜灯塔版（1.01））后端 `p/a/api/server/`  
目标：**上线前**把数据库底座定为 PostgreSQL，避免上线后“有真实数据再迁库”的高风险操作；同时保留 **1 分钟回滚**到 SQLite 的能力。

---

## 1. 结论（执行口径）

- **主站/统一 API** 与 **AI 行情官** 数据库 **分开**（避免相互影响、便于独立迭代与风控隔离）。
- AI 行情官上线前 **直接使用 PostgreSQL**（推荐），但：
  - 与主站分库：例如 `ai24x_core`（主站/统一 API）与 `ai24x_a`（AI 行情官）
  - 或同库分 schema（不如分库直观，除非你们强制一库策略）
- **回滚必须可用**：PG 失败时可立刻切回 SQLite（配置切换 + 重启）。

---

## 2. 风险说明（你最担心的点怎么压住）

### 2.1 切 PostgreSQL 会不会更容易崩溃？
会新增“网络数据库”相关故障面，但可控：

- 连接串错误 / 端口未开放 / PG 服务未启动 → 启动失败或接口 500
- 权限不足 / 库不存在 → 启动失败或写入失败
- 少量 SQL/类型差异 → 个别功能异常

**控制手段**：上线前演练 + 健康检查 + 可回滚开关。

### 2.2 PG 出错能不能马上恢复到老库？
可以，但前提是遵守铁律：

- **迁移过程必须“停写”**（维护模式），避免 SQLite 与 PG 数据分叉。
- **迁移前必须备份 SQLite 文件**（回滚保险）。
- DB 选择必须做成 **环境变量开关**，回滚只需要改配置并重启进程。

---

## 3. 数据库与身份统一：提前规划但不强行合库

你后期可能想“主站与 AI 行情官统一用户数据”。建议采用：

- **统一身份层（Identity）**（未来在主站侧落地）
- **业务数据分域**：AI 行情官仍保留自己的业务表，通过 `identity_id` 绑定即可

这样未来统一账号不需要搬家业务表，冲突也更好处理。

---

## 4. 最小落地设计（必须做到的 4 件事）

### 4.1 数据库选择开关（可回滚）

AI 行情官后端当前使用以下环境变量（与 `p/a/api/server/app/config.py` 对齐）：

- `AI24X_DB_KIND=sqlite|pgsql`
- `AI24X_DB_PATH=./data/ai24x.db`（SQLite 路径）
- `AI24X_DATABASE_URL=postgresql://user:pass@host:5432/ai24x_a`（PostgreSQL 连接串）

原则：

- **默认仍可用 SQLite**（对小白更稳、便于快速恢复）。
- 当你准备好 PostgreSQL 后，将 `AI24X_DB_KIND=pgsql` 并配置 `AI24X_DATABASE_URL`，即可切换到 PG。

### 4.2 账本化（关键数据只追加）
以下数据必须“可追溯、可对账、可回放”：

- 扣次流水（quota ledger）
- VIP 变更流水（vip ledger）
- 邀请奖励流水（reward ledger）
- 订单流水（接支付时再加，但结构上预留）

### 4.3 备份（上线前就要有）

- **SQLite 冷备**：迁移前复制 DB 文件（带时间戳）。
- **PG 备份**：上线后至少每日 `pg_dump`（保留 7/30 份）。
- **配置备份**：环境变量/密钥单独保存（禁止入 Git）。

### 4.4 回滚演练（上线前必须做一次）

- 故意把 PG 连接串改错 → 服务应失败
- 切回 SQLite → 服务应恢复
- 验证：`/health`、登录、quota、kline 扣次（最小链路）

## 5. 执行步骤（按顺序，不跳步）

### 5.1 上线前准备

1. **Windows 裸机安装 PostgreSQL**（推荐统一版本：PostgreSQL 15）。
2. 为每个环境创建独立数据库（不混用）：
   - 预演（副脑01）：`ai24x_a_pre`
   - 国内生产（副脑03）：`ai24x_a_cn`
   - 国际生产（副脑04）：`ai24x_a_intl`

域名口径（当前规划）：

- 副脑01（预演）：`a1.ai24x.com`
- 副脑03（国内生产）：`a.ai24x.com`
- 副脑04（国际生产）：`a4.ai24x.com`
3. 创建数据库用户并授予该库权限（最小权限，密码只保存在机器本地 `.env`）。

### 5.2 迁移（停写迁移，最稳）

1. **维护模式**：暂停写操作（登录/扣次/发奖等）。
2. **备份 SQLite**：复制原 DB 文件到安全位置（即使你要上 PG，也建议保留一份冷备）：
   - `ai24x.db` → `ai24x.db.bak-YYYYMMDD-HHMMSS`
3. **初始化 PG 表结构**（由后端启动时创建、或运行初始化脚本）。
4. **导入数据**（若上线前已有少量测试数据也建议走一遍流程）。
5. **校验**：
   - 用户数、quota 行数、ledger 行数、最近 N 条记录一致
6. **切换到 PG**（改环境变量）并重启后端。
7. 解除维护模式。

### 5.3 回滚（1 分钟级）

触发条件（任一满足即可回滚）：

- 服务启动失败、/health 异常
- 登录/扣次出现不可恢复的错误
- PG 连接不稳定影响用户

回滚步骤：

1. 进入维护模式（暂停写）
2. 配置切回 SQLite：
   - `AI24X_DB_KIND=sqlite`
   - `AI24X_DB_PATH=<备份或原库路径>`
3. 重启后端进程
4. 验证 `/health`、登录、quota、kline
5. 解除维护模式

---

## 6. 验收清单（上线前必须全部打勾）

- [ ] PG 可连接（从部署机/容器实际连接验证）
- [ ] 后端在 PG 模式可启动，`GET /health` 200
- [ ] 登录 OK（拿到 token），`GET /api/me` OK
- [ ] `kline` OK，扣次 OK（失败不扣、去重不重复扣）
- [ ] 备份脚本/命令可执行（至少手动跑一次）
- [ ] 回滚演练通过（PG 故障 → SQLite 恢复）

---

## 7. 备注（对外合规与运营）

- 所有对外口径避免“收益承诺/荐股指令”；
- 数据源波动应通过缓存/去重/熔断保护用户体验；
- 付费数据源开关与 VIP 优先策略保持可配置、可观测。
